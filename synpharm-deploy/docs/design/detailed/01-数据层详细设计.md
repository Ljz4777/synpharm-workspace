## 2. 全局约定（本设计确立，权威）

| 约定 | 取值 | 依据 |
|---|---|---|
| 引擎 / 字符集 | `InnoDB` / `utf8mb4` / `utf8mb4_unicode_ci` | 与既有 8 张平台表一致 |
| 主键 | `id BIGINT PRIMARY KEY AUTO_INCREMENT`（MyBatis-Plus `IdType.AUTO`） | 设计书 §0.3 D3 |
| 对外标识 | 业务编号 `*_no`（`project_no`/`run_no`/`job_no`/`report_no`/`experiment_no`/`set_no`/`session_no`），唯一索引；**取代 UUID** | D3 |
| 时间 | 一律 `DATETIME`（服务端 `Asia/Shanghai`） | §3.1 |
| 金额/得分 | `DECIMAL`，**禁用 `FLOAT/DOUBLE`** | §3.1 |
| 枚举 | `VARCHAR` + `COMMENT` 列全取值，**不用 MySQL `ENUM`**（扩展需 DDL） | §3.1 |
| 大对象 | 一律不落库；落 `file_asset`，表内只存 `*_uri` / `*_asset_id` | §3.1 |
| 外键 | **必建**，命名 `fk_<缩写>_<目标>`；批量日志表除外（避免写放大） | §3.1 |

### 2.1 逻辑删除与审计列规则（勘误 R-02）

| 表类型 | `deleted` | `created_at` | `updated_at` | 例 |
|---|---|---|---|---|
| **可变实体** | ✅ `TINYINT NOT NULL DEFAULT 0` | ✅ | ✅ `ON UPDATE` | `design_project`、`target`、`candidate_molecule`、`constraint_set`、`design_tool`、`wet_experiment`… |
| **追加型日志/明细** | ❌ 不设 | ✅ | ❌ 不设 | `molecule_edit_log`、`evaluation_result`、`agent_step`、`tool_invocation_log` |

**追加型不设 `deleted` 的理由**：① 只增不改，逻辑删除无意义；② 加 `deleted` 会污染其幂等唯一键（如 `uk_run_mol_metric`），使"重跑评估"无法用唯一键实现幂等。

### 2.2 唯一键与逻辑删除的语义（**必读**）

沿用平台表既有约定：**唯一键不含 `deleted`**（先例：`sys_user.uk_email`、`batch_task.uk_batch_id`）。

> **含义**：一条记录被逻辑删除后，其唯一值**不释放**，不可重建同名对象。

这与设计书 §2.1「跨聚合不做级联删除，仅以 `deleted` 逻辑删除（保留科研数据）」的精神一致 —— 同一项目内的同一分子/同一绑定关系，一旦历史存在过就应保留唯一性。
**若未来出现"删除后重建同名对象"的需求**，必须改为归档语义（如 `project_no` 追加 `-ARCH` 后缀并保留原值在审计字段），**不要**把 `deleted` 塞进唯一键（会引发"多次删建后唯一键冲突"的新问题）。

## 3. 执行顺序与延迟外键（勘误 R-05）

`docker-entrypoint-initdb.d` 按**文件名字母序**执行，因此**文件编号顺序即执行顺序**。FK 依赖必须在该顺序下自洽。

```
00_create_database.sql                       ← 建库（entrypoint 亦会先建 MYSQL_DATABASE）
01_ ~ 10_    平台表（既有；01~06 含 DROP TABLE，仅适用空库）
11_ ~ 25_    设计域
26_ ~ 29_    智能体（二阶段）
30_ ~ 35_    新增表
36_design_domain_revision.sql    ← 修订 + ★延迟外键收敛点
37_design_seed_data.sql          ← 种子（幂等）
38_design_index_tuning.sql       ← 可选：函数索引 / 归档辅助索引
```

## 4. 关键设计决策

### 4.1 双轨去重键（小分子 vs 生物大分子）

| 分子形式 | 去重键 | 唯一索引 | 空值处理 |
|---|---|---|---|
| 小分子 | 标准化 `InChIKey` | `uk_project_inchikey (project_id, inchikey)` | 生物大分子 `inchikey` 为 `NULL` → 不受约束 |
| 生物大分子 | `sha256(规范化序列)` | `uk_project_sequence (project_id, sequence_hash)` | 小分子 `sequence_hash` 为 `NULL` → 不受约束 |

利用 MySQL「唯一索引允许多个 NULL」实现两套键互不干扰（实测：同项目内 1 个小分子 + 2 个生物大分子共存）。

**规范化规则必须在两端一致**（`DdiDrugResolver` 已有先例）：
- 序列：去空白、统一大写、`\n` 归一为无分隔；
- SMILES：RDKit `MolToSmiles` 后再算 InChIKey。

### 4.2 权重与综合得分（勘误 R-08）

- `metric_definition.weight` 之和不要求为 1（内置指标实测 `Σw = 1.05`）；
- 综合得分按**实际启用指标集合**归一化：`S = 100 × Σ(wᵢ·xᵢ) / Σ(wᵢ, i∈启用)`；
- `evaluation_run.metric_weights` 存**权重快照** ⇒ 同一 run 重算得到同样分数（可复现）；
- `available=false` 的指标**不进入分母**，并在响应中回传 `redistributed[]` 说明权重去向（红线 R1）。

### 4.3 能力与真实性的数据落点（红线 R1/R2）

```
design_tool.available / probe_msg      ← 能力事实的唯一权威（由 probe 回写）
        ↓ 快照
evaluation_result.realness            ← 结果侧的不可篡改留痕
evaluation_result.source_tool_id      ← 追到具体工具（FK 到 design_tool）
evaluation_result.success = 0         ← 模型静默兜底 / 引擎不可用；不计入排序
design_report.capability_note          ← 报告生成时的能力边界声明（强制）
wet_experiment.error_delta             ← 实测准确率的原始数据
```

**四条硬约束**（§1.6）在数据层的实现：
1. `available=false` 的指标不进分母 → 由 `evaluation_result` 的 `success` 与运行时权重归一化共同保证；
2. 有效性无法确证的数值必须 `success=0` 且不计入排序 → `idx_success (run_id, success)` 支撑"只用成功项算分"的查询；
3. 报告引用预测值必须附实测 `R²/MAE/命中率 + 样本量` → `wet_experiment` 的 `error_delta`/`is_hit` + `idx_accuracy` 支撑；
4. UI 置灰并给出原因 → `design_tool.probe_msg` 直接下发前端。

### 4.4 候选版本链（不落 `version_no`）

血缘由 **`parent_mol_id` 自引用**表达；`version_no` 由**拓扑位置**（到根的深度）实时计算，API 层返回 `lineageDepth`，**不落库**（避免并发分配竞争）。
成环防护三层：① 父候选创建后不可改；② 编辑限同项目；③ 服务层沿父链上行校验（不用 DB 约束，避免每次编辑跑递归）。

### 4.5 「一主靶点」与「一口袋选定」用生成列实现

MySQL 不支持带 `WHERE` 的部分唯一索引，故用 **STORED 生成列 + 唯一索引**：

```sql
-- project_target：仅主靶点非空
primary_project_id BIGINT GENERATED ALWAYS AS (IF(is_primary = 1, project_id, NULL)) STORED,
UNIQUE KEY uk_primary_target (primary_project_id)

-- binding_pocket：仅选定口袋非空
selected_structure_id BIGINT GENERATED ALWAYS AS (IF(is_selected = 1, structure_id, NULL)) STORED,
UNIQUE KEY uk_structure_selected (selected_structure_id)
```

实测：第二个主靶点插入 → `ERROR 1062 Duplicate entry '990001' for key 'project_target.uk_primary_target'`。
**为何用 DB 层**：这是**逻辑不变式**（生成只能有一个基准靶点、设计只能用一个口袋），不存在需要放宽的场景。
**反之**「一项目一未关闭轮次」刻意不加（勘误 R-07）—— 需允许并行对照实验。

## 5. `design_library_item.meta_json` 结构约定

| `category` | `meta_json` 结构 | 用途 |
|---|---|---|
| `DISEASE` | `{"meshId","icd10","alias":[]}` | 疾病选择 |
| `TARGET` | `{"uniprotId","targetId","geneName","defaultStructures":["1M17"]}` | 关联 `14_target`，避免重复维护序列 |
| `MODALITY` | `{"defaultDimensions":[]}`、`{"defaultEditStrategies":[]}`、`{"seqRequired":bool}` | **决定默认评估维度与默认编辑策略**（立项时一键带出） |
| `CONSTRAINT_TEMPLATE` | `{"severity","rules":[{"ruleType","params"}]}` | 一键生成 `constraint_rule` |
| `OBJECTIVE` | `{"dimension","operator","threshold","unit"}` | 支撑"目标驱动加权" |
| `ASSAY` | `{"resultUnit","higherBetter","typicalRange":[min,max]}` | 湿实验录入的默认单位与方向 |

`MODALITY.meta_json` 是**多模态差异化的单一来源**：抗体默认带 `IMMUNOGENICITY` 维度与 `HUMANIZATION` 策略，小分子则不带。

### 6.2 复现步骤

```powershell
# 1) 把 sql 拷进 MySQL 容器
docker cp d:\synpharm-workspace\synpharm-backend\sql synpharm-dev-mysql:/tmp/allsql

# 2) 干净重来：00_ 建库（无默认库）+ 01_~38_（带 --database，等同 entrypoint 行为）
docker exec synpharm-dev-mysql sh -c 'cd /tmp/allsql
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" -e "DROP DATABASE IF EXISTS synpharm;"
  mysql -uroot -p"$MYSQL_ROOT_PASSWORD" < 00_create_database.sql
  for f in $(ls *.sql | sort); do
    case "$f" in 00_*) continue;; esac
    echo "-- $f"; mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --database=synpharm < "$f" || echo "FAILED $f"
  done'

# 3) 幂等复跑设计域
docker exec synpharm-dev-mysql sh -c 'cd /tmp/allsql
  for f in $(ls 1[1-9]_*.sql 2[0-9]_*.sql 3[0-8]_*.sql | sort); do
    mysql -uroot -p"$MYSQL_ROOT_PASSWORD" --database=synpharm < "$f" || echo "FAILED $f"
  done'
```

> ⚠ 第 2 步会 **DROP 整个 `synpharm` 库**（含平台数据）。仅用于验证；生产/日常勿用。
> ⚠ `01_`~`06_` 在**非空库**重跑会因 FK 报 `3730`（既有设计，勘误 P-3），故第 2 步是唯一正确的"整库重建"方式。

## 8. 迁移与演进策略

| 场景 | 策略 |
|---|---|
| 新增字段 | 追加新脚本 `39_`/`40_`…，用 `information_schema` 守卫；**不改**已发布脚本 |
| 修正字段 | 同上（`MODIFY` 天然幂等，但仍建议守卫 + 注释） |
| 新增表 | 取下一个空号；若与前序表有 FK 依赖，按 §3 判断是否需要延迟到修订脚本 |
| 数据回填 | 单独 `NN_design_migration_*.sql`，幂等（`UPDATE ... WHERE` 或 `ON DUPLICATE KEY`） |
| 回滚 | 设计域**不做 DROP 回滚**（保留科研数据）；如需下线，先逻辑删除 + 归档 |
| 容量 | `evaluation_result` 达 1000 万行前必须落地分区/归档（见 [`05-开放问题解决方案.md`](./05-开放问题解决方案.md) Q5） |
