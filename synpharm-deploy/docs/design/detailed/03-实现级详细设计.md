**依赖方向铁律**：`api → application → domain ← infrastructure`。
`domain` **不得**依赖 `infrastructure`（仓储走接口）；`api` **不得**直接调用 `infrastructure`。

## 2. 分层职责与禁止事项

| 层 | 做 | **不做** |
|---|---|---|
| `api` | 参数校验（`@Valid`）、归属校验、DTO 装配、状态码（201/202） | 业务判断、事务、直接调 Mapper |
| `application` | 用例编排、`@Transactional`、发 MQ（`afterCommit`）、组装跨聚合视图 | 写 SQL、拼 JSON、调 HTTP |
| `domain` | 约束求值、得分计算、血缘、能力规则 | 任何 IO（DB/HTTP/Redis） |
| `infrastructure` | SQL/Mapper、WebClient、MQ、Redis、对象存储 | 业务规则 |

> **红线 R3 的代码体现**：MCS / 描述符 / 约束求值**必须在服务端**。前端 `/design` 的对比面板只允许调用 `POST /api/design/compare/candidates`；任何在前端实现化学计算的 PR 一律驳回。

## 3. 事务边界总表（红线 R5）

**铁律**：① DB 事务内只做本地写；② MQ 投递一律 `afterCommit`；③ 跨服务 HTTP **不进事务**；④ 批量写入按批独立事务。

| 用例 | 事务内（本地写） | 事务外（afterCommit / 事务后） |
|---|---|---|
| 创建项目 | `design_project` + `project_target` ×N + （可选）`constraint_set` + `constraint_rule` | — |
| 绑定约束集激活 | `design_project.active_constraint_set_id` + `constraint_set.status/version` | — |
| 开启轮次 | `design_round` 插入 + `design_project.current_round_id` | — |
| **提交生成** | `design_job(PENDING)` + `generation_run(PENDING)` | **MQ 投递**（`afterCommit`） |
| **执行编辑** | `candidate_molecule(EDITED)` + `molecule_edit_log`（同事务） | 同步快评写 `evaluation_result`（**另一短事务**） |
| 编辑预览 | —（不落库） | 调 FastAPI `/v1/molecules/edit`（**无事务**） |
| **批量评估** | `evaluation_run(PENDING)` + `design_job` | MQ 投递；**消费端每批结果一个独立事务** |
| 生成/评估消费 | 每批 `candidate_molecule` / `evaluation_result` 独立事务 + 更新 `*_run` 统计 | 进度推 Redis / SSE（**事务外**） |
| **报告生成** | `design_report(PENDING)` + `design_job` | MQ 投递 |
| **报告审批** | `design_report.decision*` + （REVISE）插入修订版占位 + （APPROVED）预写 `wet_experiment(PLANNED)` | 送样通知（邮件等）放 `afterCommit` |
| 录入湿实验 | `wet_experiment`（含服务端算出的 `error_delta` / `is_hit`） | — |
| 回灌校准 | `design_job` + 更新 `wet_experiment.feedback_*` | MQ 投递 → 产物登记 `file_asset` → 回写 `calibration_id` |
| 文件上传去重 | `file_asset`（命中则 `ref_count+1`）+ 引用方更新 | 未命中时**先上传对象存储再**开事务（避免长事务持锁） |

**关键反例（历史问题 `D-05`）**：单条预测曾在事务内做 30~60s 外部 HTTP。设计域**严禁**复现该模式。

## 4. 并发与幂等

### 4.1 三层防线

| 层 | 手段 | 覆盖 |
|---|---|---|
| L1 业务幂等键 | `design_job.uk_idempotent_key`：同键且未终态 → 返回既有 job（`data.reused=true`） | 重复点击"提交生成/评估/报告" |
| L2 业务唯一键 | `uk_project_inchikey`、`uk_project_sequence`、`uk_run_mol_metric`、`uk_sha256`、`uk_primary_target`、`uk_structure_selected` | 并发重复产出同一分子/结果/文件；多主靶点；多选定口袋 |
| L3 乐观锁 | 更新类接口的 `version` / `If-Match` → 冲突 `409 STALE_OBJECT` | 项目、约束集、报告审批的并发编辑 |

### 4.2 唯一键冲突 → 业务错误码的归一化（**必须实现**）

数据库唯一键抛的是 `SQLIntegrityConstraintViolationException`（`ERROR 1062`），**不能直接透给前端**。
在 `application` 层统一转换：

| 唯一键 | 归一化错误码 | 附带数据 |
|---|---|---|
| `uk_project_inchikey` / `uk_project_sequence` | `CANDIDATE_DUPLICATED` / `MOLECULE_DUPLICATED` | `details.existingId`（先查一次拿 id） |
| `uk_primary_target` | `DESIGN_PRIMARY_TARGET_EXISTS` | — |
| `uk_structure_selected` | `POCKET_NOT_SELECTED` 的反向：提示"请先取消原选定口袋" | `details.currentPocketId` |
| `uk_project_target` | `DESIGN_TARGET_DUPLICATED` | — |
| `uk_idempotent_key` | **不报错**：捕获后改为查既有 job 并返回（幂等成功路径） | `data.reused=true` |

**实现要点**：先查询后插入（降低冲突概率）**且**捕获 1062（兜住并发窗口）。二者缺一不可。

### 4.3 「恰好一个主靶点」

- 请求校验：`targets` 中 `isPrimary=true` 的数量必须为 1（避免"一个都没有"）；
- 数据库兜底：`uk_primary_target` 防"多个"（并发窗口）。

## 5. 关键时序

### 5.1 生成（异步）

```
Client                 Controller        GenerationAppService        MQ            Consumer
  │ POST generation-jobs │                     │                     │                │
  ├─────────────────────►│ 校验+归属+限流        │                     │                │
  │                      ├────────────────────►│                     │                │
  │                      │                     │ 事务: design_job     │                │
  │                      │                     │  + generation_run    │                │
  │                      │                     │  afterCommit ───────►│ 投递(generate)  │
  │◄── 202 {jobId,jobNo} ┤◄────────────────────┤                     │                │
  │ GET /jobs/{jobNo}    │                     │                     │                │
  ├─────────────────────►│                     │                     ├───────────────►│
  │                      │                     │                     │  调 /v1/generate│
  │                      │                     │                     │  分批落库(各自事务)
  │                      │                     │◄── 更新 run 统计 ────┤                │
  │◄── progress/candidate（SSE，或轮询）        │                     │                │
```

### 5.2 编辑（同步，保存即编译）

```
Client ──POST /candidates/{id}/edits──► EditController
        │ previewOnly=true ?
        ├─ 是 → 调 /v1/molecules/edit（无事务）→ 200 返回，不落库
        └─ 否 →
             事务 A: 插 candidate_molecule(EDITED) + molecule_edit_log      ← 短事务
             事务 B: 同步快评（/v1/evaluate/properties）写 evaluation_result + 更新 total_score
             201 返回 { candidateId, metrics[], constraintRag[], totalScore }
```

**性能预算**（P95 < 1.5s，§8.2）：`/v1/molecules/edit` ≤ 400ms、`/v1/evaluate/properties` ≤ 600ms、其余为库操作。
若 `evaluateInline=false`，事务 B 改投 MQ（牺牲"保存即编译"手感换取稳定性）。

### 5.3 评估（分批独立事务）

```
Consumer: 取候选批次(默认 200) → 调 /v1/evaluate/* → for 每批 { 事务: 批内 evaluation_result upsert + 计数 }
           ↑ 每批独立事务，避免长事务（R5）
     失败处理: 单批失败不中断整批 → run.status = PARTIAL + 逐项 error_msg（红线 R1：不得掩盖）
```

### 5.4 报告审批

```
PATCH /reports/{id}/decision
  事务: ① 校验 decision/version（乐观锁）
        ② REPORT_ALREADY_DECIDED 检查（同 version_no 只能决策一次）
        ③ 写 decision/decision_by/decision_at/decision_note
        ④ REVISE → 插入修订版占位(revision_of, version_no+1)
           APPROVED → 预写 wet_experiment(PLANNED) 清单
  afterCommit: 通知（邮件/站内信）
```

## 6. 能力注册与探测（红线 R1/R2 的运行时）

### 6.1 `ToolRegistryService`

```
@Scheduled(fixedDelay = 10min)  refreshAll()
  ├─ GET {fastapi}/v1/evaluate/capabilities        ← 引擎能力矩阵
  ├─ 合并 design_tool.capability_key → available
  └─ 写回 design_tool.available / probe_msg / last_probe_at（独立事务）

@Async  probe(toolId)           按需探测（POST /tools/{id}/probe）
```

**判定规则**（单一权威）：

| 条件 | `available` | `probe_msg` |
|---|---|---|
| 引擎能力矩阵中对应键为 `true` 且 `enabled=1` | 1 | `null` |
| 引擎能力为 `false` | 0 | `引擎 X 未部署` |
| 探测请求失败（超时/连不上） | 0 | `引擎不可达：<原因>` |
| 从未探测过 | 0（建表默认） | `尚未探测` |

> **禁止**：把 `available` 暴露为可写 API 字段（否则等于允许伪造能力）。`POST /tools` 与 `PATCH /tools/{id}` 均**忽略**该字段。

### 6.2 能力的三个使用点

1. **命令注册表**：`GET /capabilities` + `design_tool.available` → 不可用命令置灰并给出 `probeMsg`；
2. **评估启用指标**：`available=false` 的指标不得进入综合得分分母，并在响应回传 `redistributed[]`；
3. **结果留痕**：写 `evaluation_result` 时快照 `realness` + `source_tool_id`。

**静默兜底识别**（红线 R2）—— 引擎返回"看似正常但无意义"的值时必须记 `success=0`：

| 症状 | 判定 |
|---|---|
| 置信度恒为 `0.5` / 亲和力恒为 `0` / `interactions` 恒空 | `success=0`（历史 `C-03`：KAN-MoDTI 崩溃时返回 `[0],[0],[0.5]`） |
| `algo_type` 与请求不符的回包 | `success=0` + `error_msg` |
| 响应缺必填 metric 字段 | `success=0` |

## 7. MQ 编排

| 队列 | 消息体（关键字段） | 消费者行为 | 重试/死信 |
|---|---|---|---|
| `design.generate` | `jobId, generationRunId, projectId, roundId, strategies, seed, targetCount` | 调 `/v1/generate`，分批落 `candidate_molecule`，回写统计 | 3 次指数退避 → `design.dlq` |
| `design.evaluate` | `jobId, evaluationRunId, scope, candidateIds, metrics, weightsSnapshot` | 分批调 `/v1/evaluate/*`，每批独立事务写结果 | 同上 |
| `design.pocket` | `jobId, structureId, methods, topN` | 调 `/v1/pockets/detect`，落 `binding_pocket` | 同上 |
| `design.report` | `jobId, reportId, evaluationRunId, topN` | 装配正文（含能力边界 + 实测准确率）写 `body_json`/`body_md` | 同上 |
| `design.feedback` | `jobId, projectId, experimentIds, mode, batchNo` | 调 `/v1/feedback/*`，登记 `file_asset`，回写 `calibration_id` | 同上 |
| `design.job.status` | `jobNo, status, totalCount, doneCount, result, errorCode, errorMsg` | **反向通道（设计服务消费）**：更新 `design_job`；先判「未终态」，终态忽略重复回报 | 同上 |

> **`design.job.status` 是阶段 2B 补的**：上表原本只定义「设计服务 → 计算层」的下发方向，
> 但计算层是独立服务、不能直连设计服务的库，而规范要求「DB 为权威」，
> 因此「计算层 → 设计服务」的回报必须走 MQ。该队列同样配死信。

**共同约定**：
- 消息带 `jobId`，消费端**先校验 job 未终态**（防重复消费）；
- 所有成功率/失败率**必须**区分 `SUCCEEDED` / `PARTIAL` / `FAILED`，`PARTIAL` 需写逐项 `error_msg`；
- 幂等：`evaluation_result` 依赖 `uk_run_mol_metric` 做 upsert（重复消费不翻倍）；
- 进度推 Redis `design:progress:{jobNo}`（TTL 24h）+ SSE 频道 `design:sse:{jobNo}`。

## 8. 缓存

| Key | 内容 | TTL | 失效 |
|---|---|---|---|
| `design:progress:{jobNo}` | 进度快照（`status/progress/doneCount/totalCount`） | 24h | 终态后保留 |
| `design:capabilities` | 引擎能力矩阵缓存 | 5min | probe 刷新时删 |
| `design:tool:{toolCode}` | 工具元数据 + `available` | 5min | `PATCH /tools` 时删 |
| `design:cmd:{projectId}` | 命令注册表（按项目状态 + 能力过滤后的结果） | 60s | 项目状态变更时删 |
| `design:ratelimit:{userId}:{api}` | 限流计数 | 1min | — |
| `design:sse:{jobNo}` | 事件流（Redis Pub/Sub 或 Stream） | 24h | — |

> **DB 为权威**：Redis 丢失时进度可从 `design_job` 重建（只丢 `candidate`/`metric` 增量事件，不丢事实）。

## 9. 错误处理

- 扩展既有 `ErrorCode` 枚举（`com.synpharm.exception.ErrorCode`），新增 [`02-接口层详细设计.md`](./02-接口层详细设计.md) §2 的全部 `errorCode`；
- **复用** `GlobalExceptionHandler`，**不新增**全局处理器；
- `BusinessException(ErrorCode, message)` + `details`（Map）承载 `existingId` / `readyBlockers` / `fieldErrors` / `probeMsg`；
- **禁止**在响应中泄露堆栈（`INTERNAL_ERROR` 只记日志）；
- `assertOwnership` **fail-closed**：`ownerId == null` 必须抛错（不得沿用历史 `B-12` 的 fail-open 写法）。

## 10. 归属校验（红线 R4）

```java
@Component
public class OwnershipGuard {
    /** 归属不符 → 抛 404（不是 403），避免资源探测 */
    public <T> T require(T entity, Long ownerId, ErrorCode notFound) {
        if (entity == null || ownerId == null || !ownerId.equals(ownerOf(entity))) {
            throw new BusinessException(notFound);   // 404
        }
        return entity;
    }
}
```

**必查清单**（每个入口都要）：项目、轮次、靶点、结构、口袋、约束集、生成任务、候选、编辑产物、评估任务、任务、报告、实验、文件、工作台状态。
`403 FORBIDDEN` **仅**用于非归属类（如未来管理员接口）。
