## 1. 致命级（阻塞落库，已修）

### R-05 🔬 §3.2「编号顺序即落库顺序」与 FK 依赖冲突

**现象**：`docker-entrypoint-initdb.d` 按**文件名字母序**执行，而设计书的编号顺序存在两处 FK 前向引用：

| 脚本 | 引用的表 | 该表所在脚本 | 结果 |
|---|---|---|---|
| `12_project_target` | `target(id)` | `14_target` | `ERROR 1824 Failed to open the referenced table 'target'` |
| `11_design_project` | `constraint_set(id)`（`active_constraint_set_id`） | `17_constraint_set` | 同因（本次一并补建） |

**复现**：`mysql < 12_project_target.sql` → `ERROR 1824 (HY000) at line 15`。

**修正**：两个外键**延迟到 `36_design_domain_revision.sql` 补建**（该脚本最后执行，此时所有表已就绪）。`12_` 中保留注释说明原因。
**为何不改编号**：编号被 8 份文档引用，且 `11_~25_` 已"预留"给设计域；改编号的破坏面远大于延迟 FK。这与仓库既有做法一致（`08_batch_task_alter.sql` 存在的理由相同）。

### R-06 🔬 设计书 §3.3 的 DDL 使用「相邻字符串字面量拼接」，MySQL 8 无法执行

**现象**：设计书多处长枚举 `COMMENT` 写成折行拼接：

```sql
category VARCHAR(30) NOT NULL
         COMMENT 'CONSTRAINT/PROPERTY/DRUGLIKENESS/SAFETY/.../'
                 'ACTIVITY/SELECTIVITY/DOCKING/ADMET',
```

MySQL 8 在**列定义的 `COMMENT` 位置**不接受相邻字面量拼接（尽管 `SELECT 'a' 'b'` 是合法的）。

**实测复现**（最小用例）：

```sql
CREATE TABLE _t (a VARCHAR(10) COMMENT 'AB/' 'CD', b VARCHAR(10) COMMENT 'EF/GH');
-- ERROR 1064 (42000) at line 1: ... right syntax to use near ''CD', ...
```

**影响面**：5 处 / 4 个文件（`18_constraint_rule`、`21_molecule_edit_log`、`22_metric_definition`、`35_wet_experiment`）。
**修正**：全部合并为单行完整字面量；`18_` 中保留一条说明性注释。**注意**：模块文档 `02~06` 里同类写法同样不可执行，落地时需同样处理（本次已一并处理）。

### R-14 🔬 `36_design_domain_revision.sql` 原文不幂等，与 §8.2 验收项自相矛盾

**现象**：§8.2 要求「`36_`/`37_` 在既有库执行成功且**幂等**（可重复执行不报错）」，但 §3.4 给出的实现是裸 `ALTER TABLE ... ADD COLUMN` —— 第二次执行必然 `ERROR 1060 Duplicate column`。

**修正**：重写为「存储过程 + `information_schema` 守卫」，按列/索引/外键分组判存后再改。同一技巧仓库内已有先例（`08_batch_task_alter.sql`）。
**实测**：`11_`~`38_` 连跑两轮，第二轮 **28/28 OK**。

**现象**：设计书 §2.2A 把 `sys_user_research_profile` 列为「9 张平台复用表」之一。实际：

### R-16 🔬 设计书 §8.1 声称「PlantUML 图 ×7 ✅ 语法校验通过」，实测 2 张不通过

**实测方法**：PlantUML 1.2024.7（`java -jar plantuml.jar -checkonly`），对 `docs/design/**/*.puml` 全量校验。

| 文件 | 结果 |
|---|---|
| `uml/01-usecase.puml` | ✅ exit=0 |
| **`uml/02-component.puml`** | ❌ **exit=200**（`Some diagram description contains errors`） |
| `uml/03-class.puml` | ✅ exit=0 |
| `uml/04-sequence-main.puml` | ✅ exit=0 |
| `uml/05-sequence-feedback.puml` | ✅ exit=0 |
| `uml/06-state.puml` | ✅ exit=0 |
| **`uml/07-activity.puml`** | ❌ **exit=200** |

**已排除的原因**（逐一实测）：

| 假设 | 结论 |
|---|---|
| UTF-8 BOM 导致首行 `@startuml` 未被识别 | ❌ 13 个 .puml 全部**无 BOM** |
| 不可见字符（NBSP / 零宽 / 控制符） | ❌ 全部 `clean` |
| 换行符（CRLF vs LF） | ❌ 两者都能通过（本次新增的 6 张为 CRLF 且全部 exit=0） |
| 泳道语法 `\|#color\|name\|` | ❌ 合法颜色下通过 |
| `if/elseif/else/endif` + 泳道切换 + 分支内 `stop` | ❌ 通过 |
| `while ... endwhile` 内含泳道切换与嵌套 `if` | ❌ 通过 |
| `fork ... fork again ... end fork` | ❌ 通过 |
| `cloud { ... }` 嵌套、`note top of <package>`、`skinparam ArrowColor`、中文标题含连字符 | ❌ 均通过 |

**定位状态**：未定位到具体行。PlantUML `-checkonly` 在该版本**只给汇总、不给行号**；按注释分隔线做分段删除时，删头/删尾会移除 `@startuml`/`@enduml` 造成"假通过"，中段 4 段删除均为 exit=200，故无法用此方法收敛。

**影响**：设计书 §8.1 交付清单的第 2 项（「PlantUML 图 ×7 完成，语法校验通过」）**不准确**；`02-component`（架构分工图）与 `07-activity`（端到端闭环活动图）**当前无法渲染**。
**修正建议**：~~重写这两张图（或按构造裸测的方式逐块试错）~~。
**未修原因**：属既有交付物，且重写成本与本次「进一步详细设计」的范围正交 —— 见「待办」。

**✅ 后续定位（2026-10-14）：根因是校验命令未指定 UTF-8 字符集，与图的内容和语法无关。**

| 组合（同一文件 `02-component.puml`、同一内容） | `-checkonly` | 真实渲染 |
|---|---|---|
| 无 BOM，无 `-charset` | `200` ❌ | `200` ❌ |
| 无 BOM，`-charset UTF-8` | `0` ✅ | `0` ✅ |
| 有 BOM，无 `-charset` | `0` ✅ | `0` ✅ |

上方「已排除的原因」中，**「UTF-8 BOM」这一条排除得对但与本题无关**：真正未被变化过的变量是**调用时字符集** —— 不带 `-charset UTF-8` 时 PlantUML 按 GBK 猜测输入编码，对部分内容猜错，中文被误读成 `'`、`=`、`;` 等语法字符。**加 BOM** 与 **传 `-charset UTF-8`** 两种解法等价（这也解释了为何 13 个文件同样无 BOM，却只有 2 个失败：猜测结果依内容而定）。

**⚠️ 本条勘误（R-16）与待办 A-7 已失效**：`02-component.puml`、`07-activity.puml` 及其余 11 张 PlantUML 已于 2026-10-14 全部改写为 **Mermaid 内嵌** → [`../../uml/设计域.md`](../../uml/设计域.md)。项目内**已无任何 `.puml` 文件**，「重写两张图」的待办**自动消解**。

### R-17 📝 `openapi.yaml` 的 `Target` schema 漏登记 4 个字段（v1.8.0 已补）

**现象**：契约的 `Target` schema 只有 14 个属性，而实现需要 18 个。
`description` / `pathway` / `relatedDiseases` / `knownDrugs` **四个字段在契约里根本不存在**，
但它们：

- 在 `sql/14_target.sql` 建表时就存在 —— 该脚本开头明写「字段与前端 `src/types/index.ts` 的
  `Target` 接口逐一对齐」；
- 在 `测试数据准备清单.md` §2.A 的「接口字段规格」表里逐行列了，其中 **`description` 是必填**；
- 在问题总账 C-08（靶点库整体 mock）的整改要求里也是要显示的字段。

**风险**：按契约实现会得到一个**没有功能描述、没有相关疾病、没有已知药物**的靶点库页面 ——
而这几项恰恰是用户在选择靶点时要看的依据；`src/types/index.ts` 里有、契约里没有，
前端按自己的类型写、后端按契约写，两边不会报错但**数据永远缺**。

**修正（已落地，v1.8.0）**：把 4 个字段补进 `openapi.yaml` 的 `Target`，并在 YAML 里逐条标注
「勘误 E-01（v1.8.0 补登记）」。加字段是**非破坏性**变更（只增不删），不影响既有消费方。

> 编号说明：本条在代码注释与 openapi 里引用的名字是 **E-01**（Errata 序号），
> 与本文档的 **R-17** 是同一条 —— R-xx 是评审轮内的编号，E-01 是跨文档统一引用用的序号。

**同类问题（同一轮发现，已一并处理）**：`GET /api/design/structures/{id}/pockets` 在契约里
**只登记了 `200`**，但「结构不存在」与「结构存在但没有口袋」必须可区分 —— 都用 200 +
空数组等于告诉前端「这个结构一个口袋都没有」。已补 `404`，对应错误码
`STRUCTURE_NOT_FOUND`(40454) 也补登记进规范 §4.4（那里原有三处「阶段 2B 补登记，见下」
是**悬空引用**，指向一处并不存在的说明，一并补上了）。

## 3. 设计缺陷（已修 + 记录理由）

### R-01 🔬 种子数据会把"未部署的引擎"标成可用

**现象**：§3.6 的 `design_tool` 种子未给 `available` 值，而 §3.3.3 建表默认 `available TINYINT NOT NULL DEFAULT 1` → 12 个工具全部以「可用」入库。这与红线 R1/R2（`available` 是能力事实的权威、UI 不得"点了才失败"）**直接冲突**：`vina`/`admet_ai`/`crem`/`p2rank` 都没部署。

**修正**：
1. 建表默认值改为 **`DEFAULT 0`**（语义：未探测 ≠ 可用）；
2. 种子显式写入 `available=0` + 逐条 `probe_msg`（如 `FlashPPI 权重缺失（model.safetensors）→ /health/ 报 weights_missing`）；
3. `available` / `probe_msg` / `last_probe_at` **刻意排除在 `ON DUPLICATE KEY UPDATE` 之外**，避免重跑种子覆盖线上探测结果。

**实测**：`SELECT COUNT(*) FROM design_tool WHERE available=1` → **0**。

### R-04 📝 `target_structure` 的唯一键对 AlphaFold 记录失效

**现象**：`uk_target_pdb_chain (target_id, pdb_id, chain_id)`；而 §6.2 注释明说「AlphaFold 时 `pdb_id` 为空」。MySQL 唯一索引**允许多个 NULL**，因此同一靶点可以插入**任意多份** AlphaFold 结构（`pdb_id`/`chain_id` 全为 NULL），去重形同失效。

**修正**：改为 `uk_target_source (target_id, source, source_key)`，新增 `source_key VARCHAR(80) NOT NULL`：

| source | source_key |
|---|---|
| `PDB` | `1M17:A` |
| `ALPHAFOLD` | `P00533:v4`（含版本，支持 AF 版本升级后并存） |
| `USER_UPLOAD` | `sha256 前 16 位` |

这样三种来源都有稳定且在各自语义下正确的唯一性。

### R-13 📝 `evaluation_result.inchikey` 对生物大分子无意义

**现象**：模块文档 06 定义为 `inchikey CHAR(27) NOT NULL`；但 §3.4.2 已承认生物大分子没有 SMILES/InChIKey（并放开 `candidate_molecule.inchikey`），评估结果表却仍要求非空 —— 生物大分子的评估结果将**无法写入**。

**修正**：放开为 `NULL`（与 `candidate_molecule` 一致）。`36_` 中对既有库同样做 `MODIFY`。

### R-02 📝 模块文档 DDL 未遵循设计书 §3.1 的「逻辑删除 + 审计列」约定

**现象（15 张表逐张核对）**：`§0.1` 明确「字段级设计以本文为准」，`§3.1` 规定统一 `deleted` / `created_at` / `updated_at`；但 `docs/modules/design/02~07` 的 DDL 中：

| 缺 `deleted` | `project_target`、`target_structure`、`binding_pocket`、`constraint_rule`、`molecule_edit_log`、`metric_definition`、`evaluation_result`、`workspace_state` |
| 缺 `updated_at` | 同上（除 `metric_definition` 外几乎全部） |

**修正规则（本设计确立，写入 [`01-数据层详细设计.md`](./01-数据层详细设计.md) §2）**：

- **可变实体**（可列表查询、可被修改）：补 `deleted` + `created_at` + `updated_at`；
- **追加型日志/明细**（`molecule_edit_log`、`evaluation_result`、`agent_step`、`tool_invocation_log`）：**只补 `created_at`**，不设 `deleted` / `updated_at`
  —— 理由是它们只增不改，且加 `deleted` 会破坏其幂等唯一键（如 `uk_run_mol_metric`）的语义。

**由此引出的唯一键语义（必须全体知晓）**：沿用平台表既有约定（如 `sys_user.uk_email`），**唯一键不含 `deleted`**。含义：**逻辑删除后唯一值不释放**。
这与 §2.1「跨聚合不做级联删除，保留科研数据」的精神一致；但若未来出现"删除后重建同名对象"的需求，必须改为归档语义而非直接复用唯一值。

### R-07 📝「同一项目最多一个未关闭轮次」未在 DB 层约束

**现象**：§2.1 说由服务层保证，§3 无对应约束。
**裁决**：**刻意不加**数据库约束。理由：会阻塞「并行跑两轮对照实验」这一合理科研用法；改为服务层在「开启新轮」时校验 + 在 `13_` 中写明并发窗口的处理（两人同时开轮 → 后者收到 `DESIGN_ROUND_ALREADY_OPEN`）。
**对比**：`project_target` 的「一主靶点」加了 DB 层唯一约束（`uk_primary_target`）—— 因为它是**逻辑不变式**（生成只能有一个基准靶点），不存在需要放宽的场景。

### R-08 🔬 `metric_definition` 内置指标权重之和 = 1.05 ≠ 1

已在 `22_metric_definition.sql` 文件头与 [`01-数据层详细设计.md`](./01-数据层详细设计.md) §4 写明。

## 7. 结论

1. **方向正确**：七条红线（尤其 R1 真实性边界、R2 禁止愿望式契约）是这份设计最有价值的增量，机制（`realness` + `available` + `success` + 权重重分配）可落地、可验收。
2. **原文不可直接执行**：DDL 的字面量写法（R-06）与脚本顺序（R-05）是硬阻塞；`36_` 的不幂等（R-14）与 §8.2 自相矛盾。**三者已修并实测**。
3. **两处事实性错误**：`sys_user_research_profile` 表不存在（R-03）、工具端点与引擎现状不符（R-09）。**已修**，其中 R-09 的长期形态待裁决（A-1）。
4. **一处设计缺陷值得强调**：种子把未部署的引擎标为可用（R-01）—— 这是红线 R1/R2 在自己的种子数据里被违反，已修。
5. 本次交付的 `sql/11_~38_` **已在 MySQL 8.0.46 实跑验收**（空库 40/40、幂等 28/28、唯一键/去重/外键/种子全通过）。
