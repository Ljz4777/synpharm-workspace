## Q1 · OpenAPI 3.0 规范未内联

### 现状 / 约束

设计书 §8.3 Q1：「前端联调需手写类型」。实测仓库现状：前端 `src/types/design.ts`（10.3 KB）与 `src/api/design.ts` 的 `DesignApi`（手写）**双份维护**，与后端契约无自动校验；`docs/design/` 下原本没有 `openapi.yaml`。

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 手写 `openapi.yaml`**（已采用） | 立即可用；前端类型可自动生成；无需后端先实现 | 与最终实现可能漂移；需人工维护 |
| B. 等后端实现后由 Knife4j 导出 | 零漂移；单一事实源 | 阻塞前端；后端未实现前无事可做 |
| C. 先手写、后切换（**A→B**） | 兼顾 | 需一次切换成本 |

### 建议与理由

**采用 C**：现在用 A（手写）解除前端阻塞；后端实现后切换到 B（`/v3/api-docs` 导出），并在 CI 中做**双向校验**（导出的 spec 与 `openapi.yaml` 的路径集合对齐，防止新增端点漏登记）。

### 落地动作

1. ✅ [`openapi.yaml`](./openapi.yaml)（已产出并校验：83 路径 / 99 操作 / 62 schema / 0 断链 / 0 重复 `operationId`）
2. 前端加 `openapi-typescript`：`npx openapi-typescript docs/design/detailed/openapi.yaml -o src/types/design.gen.ts`，逐步替换手写类型
3. CI 加一步：`diff <(导出 paths) <(openapi.yaml paths)`，不一致即失败
4. 后端补 Knife4j 注解后，把 `openapi.yaml` 标记为「参考实现」并改为从 `/v3/api-docs` 生成

### 现状 / 约束

| 约束 | 说明 |
|---|---|
| 现状 | `candidate_molecule.origin_type=IMPORTED` 可手工导入序列；**无生成能力** |

### 候选方案对比

| 方案 | 代表实现 | 硬件 | realness | 可解释性 | 交付周期 | 适用 |
|---|---|---|---|---|---|---|

| ② 序列语言模型 | IgLM、ProGen2、ProtGPT2 | CPU 可跑，**GPU 才实用** | `REAL`（生成式） | 低（黑盒） | 中（4~8 周 + 权重/许可） | 从头设计、序列多样性 |

| ⑤ 暂不支持 | 仅 `IMPORTED` | — | — | — | — | 冻结范围 |

### 建议与理由

**分两期，先 ① 后评估 ②/③**：

1. **S7a（立即）用方案 ①**：
   - 与「M1 纯确定性、可独立验收」的既有策略一致，**不引入新模型**，CPU 即可跑；
   - 能立即覆盖抗体/多肽设计中的**主流真实需求**（人源化、亲和力成熟位点突变、Linker 扫描）；
   - `realness=HEURISTIC` 显式标注 —— 用户看到的不是"AI 生成的新分子"，而是"按规则枚举的候选"，符合红线 R1/R2 的诚实性要求。
2. **S7b（需预算）评估方案 ②**：序列 LM 是"生成式"与 CPU 成本的平衡点；需同时确认**权重许可**（IgLM 为学术许可，商用需谨慎）。
3. **方案 ③ 暂不引入**：需 GPU 采购/租用 + GB 级权重 + 长周期，与当前"三算法 + CPU"的部署形态跨度太大。
4. **方案 ⑤ 作为兜底**：无论选哪条，`IMPORTED` 通道必须保留（真实研发中大量候选来自内部库）。

## Q4 · 校准工件（`calibrationId`）的存储与加载协议未定

### 结论

✅ **已完整解决**，见 [`04-计算层契约与校准协议.md`](./04-计算层契约与校准协议.md) §4。

要点回顾：

| 维度 | 决定 |
|---|---|
| 不做什么 | **不修改模型权重文件**（不可审计、不可回滚、2.7 GB 二进制） |
| 做成什么 | **版本化、内容寻址、不可变**的校准工件（manifest + 可选大参数文件） |

| 回滚 | 内存保留最近 20 版；`POST /v1/feedback/rollback` |

## Q5 · `evaluation_result` 长期增长（须在 1000 万行前定方案）

### 现状 / 约束

§3.7 预估：100 项目 →

| 表 | 年增长 |
|---|---|
| `candidate_molecule` | ~200 万行 |
| **`evaluation_result`** | **~3000 万行**（候选数 × ~12 指标） |
| `molecule_edit_log` | ~50 万行 |

**MySQL 8 的硬约束（这是原设计书未点明的关键）**：

> 分区表的**每一个唯一键（含主键）都必须包含全部分区列**。

因此：

```sql
-- 现有定义
PRIMARY KEY (id)
UNIQUE KEY uk_run_mol_metric (run_id, molecule_id, metric_code)
```

- ❌ **不能** `PARTITION BY RANGE(id)`：`uk_run_mol_metric` 不含 `id` → 建表即失败；
- ✅ **可以** `PARTITION BY RANGE(run_id)`：但主键必须改为 `(id, run_id)`。

### 候选方案对比

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 按 `run_id` RANGE 分区** | 主键改 `(id, run_id)`；预建 + `MAXVALUE` 兜底；定期 `REORGANIZE PARTITION` | 单表、查询无需改；删除旧分区是**秒级 DDL** | ① 主键不再是单列（MyBatis-Plus 需调整映射）② 分区管理需运维流程 ③ **已是既成事实的 PK 变更**，越晚做代价越大 |
| **B. 归档表 + 定期搬迁**（**推荐**） | 建 `evaluation_result_archive`（同结构、无 FK）；Job 按 `run_id` 批量 `INSERT…SELECT` + `DELETE`；查询走视图 `UNION ALL`（热表优先） | ① **零 schema 风险**（不动主键/唯一键）② 可在线分批做（每批 ≤ 1 万行）③ 保留策略任意可调 ④ 与 §3.7「按 `project_id` 归档」的表述一致 | ① 跨热冷查询需视图或应用层路由 ② 归档行无法再被 FK 引用（本表无被引用方，安全） |
| C. 不处理，仅靠索引 | — | 零成本 | 索引膨胀、DDL 时间线性增长、备份变慢 |

### 建议与理由

**选 B（归档表）**，理由：

1. **不动主键** —— 方案 A 要求把 `PRIMARY KEY (id)` 改成 `(id, run_id)`，这会波及 MyBatis-Plus 的 `IdType.AUTO` 语义与所有 `WHERE id = ?` 查询；而本表是**写入最热**的表，改造成本与风险最高。
2. **触发时机明确**：单表 > 500 万行（或磁盘占用 > 5 GB）即启动归档 Job；**1000 万行是硬红线**。
3. **保留策略与科研语义一致**：热表保留**最近 2 个轮次或 90 天**；归档表永久保留（科研数据不删，与 §2.1「跨聚合不做级联删除」的精神一致）。
4. **与现有设计不冲突**：`01-数据层详细设计.md` §8 已把"归档"列为容量策略；`38_design_index_tuning.sql` 已预置 `idx_run_created` 支撑归档扫描。

### 落地动作

| 步骤 | 内容 |
|---|---|
| 1 | 新增 `39_evaluation_result_archive.sql`：`CREATE TABLE IF NOT EXISTS evaluation_result_archive LIKE evaluation_result;` + 去掉 FK |
| 2 | 新增 `EvaluationArchiveJob`：按 `run_id` 分批搬迁（每批 1 万行、单批一事务），搬迁前确认该 `run` 已终态且不属于当前活跃轮次 |
| 3 | 查询路由：`GET /candidates/{id}/metrics` 与 `leaderboard` 默认只查热表（活跃轮次必在热表）；历史对比接口查归档表 |
| 4 | 监控：`evaluation_result` 行数 + 表大小进指标看板，达 500 万行告警 |
| 5 | 若未来单库仍撑不住 → 再考虑方案 A 或按 `project_id` 分库（那是 v2 话题，不在本次范围） |

> **为什么不现在就分区**：现在只有几十行数据，过早分区会引入运维复杂度且**无法回退**（分区表转普通表要重建）。归档方案在需要时**可以**升级为分区（先归档搬迁、再对热表分区），路径不冲突。

## Q6 · `version_no`（候选版本号）被有意省略

### 约束

需求要求候选有 `version_no`；设计书决定「版本由**拓扑位置**表达」。若省略，上游系统若强依赖该字段会不兼容。

### 建议与理由

**维持不落库，在 API 层实时计算并返回 `lineageDepth`**：

| 方案 | 问题 |
|---|---|
| A. 落库 `version_no`（在项目内单调递增） | 需要"项目内序列分配"，并发编辑时要么加锁（写热点）要么接受跳号；且**编辑产生的是兄弟分支而非线性版本**，"版本号"语义本身不成立（一次撤销分支后，新分支的号该是多少？） |
| **B. 不落库，实时算 `lineageDepth`**（**推荐**） | 语义正确（深度 = 到根的步数）；无并发竞争；由 `WITH RECURSIVE` 单次查询得出（§3.5② 已有查询） |
| C. 落库"项目内编辑序号"仅用于排序 | 折中，但引入与前两方案相同的并发问题，收益低 |

**兼容上游**：响应同时给 `lineageDepth` 与 `lineagePath`（祖先 id 链）。若上游强依赖 `version_no`，在其适配层用 `lineageDepth` 映射，**不在核心表引入该列**。

### 落地动作

- `Candidate` schema 已含 `lineageDepth`（见 [`openapi.yaml`](./openapi.yaml)），`02-接口层详细设计.md` 已注明"实时计算、不落库"；
- 前端谱系树用 `parent_mol_id` + `lineageDepth` 渲染，不用 `version_no`。

## A-1（新）· `design_tool.endpoint`：per-algo 别名 vs `single` + `algo_type`

### 约束

设计书 §4.6 假设存在 `/v1/predict/{dti,ppi,ddi}`；实测引擎只有 `POST /v1/predict/single`（`algo_type` 区分）。

### 候选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **A. 统一 `single`**（**短期推荐**） | 零引擎改动，立即可用；`design_tool.endpoint` 指向真实存在的端点 | 工具注册的 `endpoint` 三个工具指向同一路径，语义上不够"一个工具一个端点"（但 `input_schema` 已能表达 `algo_type`） |
| B. 补 per-algo 别名 `POST /v1/predict/dti|ppi|ddi` | 语义清晰；智能体工具描述更自然（对 LLM 友好） | 引擎需加路由（薄封装，成本低）；两套路径需长期保持一致 |

### 建议与理由

**短期 A、中期可升 B**：`design_tool` 已经**抽象**了端点差异 —— 后端 `ToolAdapter` 读 `endpoint` + `http_method` 即可调用。因此：

- 现在用 A：三个工具 `endpoint=/v1/predict/single`，`input_schema` 中含 `algo_type` 常量（`enum: [DTI]` 等）；
- 若第二阶段智能体需要更语义化的工具名，再补 B —— **只改 `design_tool` 的一行数据**，后端代码零改动。

> 已按 A 落地到 `37_design_seed_data.sql`（三条预测工具的 `endpoint` 均为 `/v1/predict/single`，`probe_msg` 注明"端点契约待冻结"）。
