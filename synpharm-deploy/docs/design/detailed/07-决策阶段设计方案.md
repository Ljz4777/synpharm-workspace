# 决策阶段设计方案

> **版本**：v1.0（2026-10-24）
> **定位**：`06-主业务三阶段设计方案.md` 的续篇。06 定下了「需求分析 → 生成 → 编辑」三段的表结构与流程，本文补上链路的后半段：**证据打包 → 决策**。
> **依赖**：`baseline_snapshot`（06 §3）、`evaluation_freeze`（06 §5 表 9）、`candidate_molecule`、`molecule_edit_log`。
> **前置状态**：阶段 C（生成）、D（最小评估 + 编辑）尚未实施。本文的 A 组口径现在就要落进 schema，B 组到阶段 E 前定。

---

## 0. 一句话定位

决策阶段不替人拍板，它做三件事：**把散落的证据整理成可评审材料**（证据打包）、**把硬性不可接受的对象挡在外面**（否决）、**把剩余对象的取舍过程记成可回放的记录**（决策记录）。

> 判据：任何一个"入选/淘汰"结论，都必须能回答三个问题 —— 依据是哪份评估快照、是哪条规则或谁做的判断、换个人按同样输入重算会不会得到同样结论。

---

## 1. 在链路中的位置

```
需求分析 ──► 生成 ──► 编辑 ──► 评估 ──► 证据打包 ──► 决策 ──► 报告 ──► 回流
   │           │        │        │          │           │        │        │
baseline   candidate  candidate  evaluation evidence  decision  report  negative
_snapshot   _molecule  版本树     _freeze    _bundle    _record   引用     _pattern
                                               ▲           ▲
                                               └───────────┘
                                          决策只读这两张表
```

**输入的唯一性**：决策阶段只读 `evaluation_freeze` 与由它派生的 `evidence_bundle`。**不读候选的当前状态** —— 否则同一份决策记录在不同时间重放会得到不同结论。

这与生成 S0 的「只读快照，不读项目当前状态」是同一条纪律。

## 2. 业务流

### 2.1 八步

| # | 步骤 | 执行者 | 输入 | 产出 | 失败处理 |
|---|---|---|---|---|---|
| D0 | 决策前置校验 | 引擎 | round_id、候选集 | 可决策候选数与阻断清单 | 无候选 / 无评估冻结 → 拒绝，不建记录 |
| D1 | 证据打包 | 引擎 | `evaluation_freeze` + 版本血缘 + 约束判定 + 风险标记 | `evidence_bundle`（逐候选一份，不可变） | 关键块缺失 → 该候选标 `DATA_INCOMPLETE`，不阻断整批 |
| D2 | 技术性复核 | 引擎 | 证据包 + `constraint_rule` HARD | 逐条约束的三态判定 | 与生成/编辑阶段的判定不一致 → 以本阶段重算为准，并记 `verdict_drift` |
| D3 | 业务性否决 | 引擎 | 证据包 + `decision_veto_rule` + 预算 | veto 清单（BLOCK / WARN） | 规则本身配置错误 → 该规则跳过并告警，不静默通过 |
| D4 | 分桶与排序 | 引擎 | 通过否决的候选 + `project_metric.weight` | 三桶 + 桶内加权排名 | 全部候选落 FAIL 桶 → 决策可提交但强制 `NO_VIABLE_CANDIDATE` 告警 |
| D5 | 名额分配 | 引擎 | 排名 + 档位（`decision_capacity_mode/value`）+ `quota_wet_lab` | SELECTED / BACKUP / REJECTED | 名额为 0 → 允许只产出 BACKUP，强制提示 |
| D6 | 人工调整 | 人 | D5 结果 | 调整后的 outcome + **必填理由** | 调整必须留痕；无理由的调整直接 400 |
| D7 | 风险接受 | 人 | 每个候选的风险点 | `risk_acceptance`（逐候选逐风险点） | `mustVerify` 且未验证 → **不接受**，只能转 DEFERRED |
| D8 | 确认与冻结 | 人 + 引擎 | D6/D7 结果 | `decision_record`（CONFIRMED）+ 回放指纹 | 回放不一致 → 拒绝确认，报 `REPLAY_MISMATCH` |

### 2.2 三个不变量

1. **证据先于判断**：`evidence_bundle` 必须在决策记录之前冻结。没有证据包的候选不能进决策表。
2. **否决不可绕过**：BLOCK 级 veto 只能通过"改数据后重新决策"消解，不能在本次决策里手动覆盖。WARN 级可以接受，但要落 `risk_acceptance`。
3. **确认即不可改**：`CONFIRMED` 之后不能修改任何 outcome。要改就新建一版（`revision_of` 指向上一版）。

## 3. 已定口径（A 组，本次采纳）

### A1 · 硬否决分两层

**决定**：技术性淘汰与业务性否决**分开**，不共用一张规则表。

| 层 | 归属 | 判据来源 | 何时生效 | 落点 |
|---|---|---|---|---|
| 技术性淘汰 | 生成 / 编辑阶段 | `constraint_rule`（severity=HARD）+ `BoundaryJudge` | S6 粗筛 / E5 剪枝 | `generation_candidate_log.filter_reason` |
| 业务性否决 | 决策阶段 | `decision_veto_rule`（新建） | D3 | `decision_candidate` + `decision_veto_hit` |

**理由**：两层的变化频率与责任人完全不同。技术性淘汰随分子形式走（小分子看 MolWt，抗体看 CDR 保守性），由算法负责人维护；业务性否决随项目走（这个靶点预算只有 8 个湿实验名额），由项目负责人维护。混在一张表里，"谁能改"和"改了影响谁"都说不清。

**配套改造**：`design_library_item` 的 `FILTER_REASON` 分类新增 `stage` 元数据，取值 `GENERATION` / `EDIT` / `DECISION`。现有 15 条按归属补齐，未标注的一律视为 `GENERATION`。

**否决规则类型（首版 6 条）**

| code | 名称 | severity | 判据 |
|---|---|---|---|
| `MUST_VERIFY_UNVERIFIED` | 必测项未验证 | BLOCK | `project_risk_item.must_verify=1` 对应风险点无实测证据 |
| `BUDGET_EXCEEDED` | 超出湿实验名额 | WARN | 排名超出 `quota_wet_lab` 余额 |
| `FTO_RISK_HIGH` | FTO 相似度过高 | BLOCK | `fto_similarity_max` 超项目阈值（默认 0.85） |
| `DATA_INCOMPLETE` | 证据包不完整 | BLOCK | 评估冻结缺失关键指标（可配） |
| `HARD_RULE_VIOLATED` | 技术性硬约束未过 | BLOCK | 兜底：D2 复核发现 HARD 未达标 |
| `MANUAL_VETO` | 人工否决 | BLOCK | 由人录入，必须带理由 |

> 最后一条 `HARD_RULE_VIOLATED` 是**兜底而不是主力**。它的存在是为了防止"生成/编辑阶段漏记原因"的分子悄悄流进决策 —— 而这正是 06 文档里"每个被筛分子必须记 filter_reason"要防的事。

### A2 · 证据包装引用，不装决策产物

**决定**：`evidence_bundle` 只装**已有的不可变事实**，不装决策阶段自己产生的任何分析。

| 装 | 不装 |
|---|---|
| `evaluation_freeze_id`（评估快照引用） | 权重调整建议 |
| 版本血缘链（root → 当前，只存 id 与 `edit_reason`） | 必测项清单（这是决策产物） |
| 每条硬约束的三态判定结果 | 风险接受记录（这是决策产物） |
| 风险标记（来自 `project_risk_item` 与实测命中） | 推荐排序分 |
| 待验证事项（由 `must_verify` 推导的**客观**遗漏项） | 优势/风险的自然语言结论 |

**理由**：证据和意见混在一起，事后就无法区分"当时数据说了什么"和"当时谁怎么想的"。审计要的是前者，复盘要的是后者，两者的保存要求不同（前者不可变，后者允许修订）。

**结构**：大字段一律存 URI + hash，JSON 里只留引用与摘要。见 §5。

### A3 · 风险接受逐候选逐风险点

**决定**：`risk_acceptance` 的唯一键是 `(decision_id, candidate_id, risk_code)`。

**理由**：整个决策记一条"我们接受了风险"等于没记 —— 谁批的、接受的到底是什么风险、有效期到什么时候，全丢了。逐点记录才能回答"这个糖基化位点风险是谁在什么时候批的，批的理由是'已有类似分子上市'还是'反正要测'"。

**硬约束**：`must_verify=1` 的风险点**不允许被接受**。只能：
- 补实测数据后重新决策，或
- 把整个候选转 `DEFERRED`（暂缓），不占用名额

**理由**：如果"必须验证"的项目可以靠点一次"接受"绕过，那它就只是建议而不是要求。

## 4. 待定口径（B 组，阶段 E 前定）

以下给出建议默认值，**先按建议实现，等有真实 `evaluation_freeze` 数据后用真候选试算再调**。表中"何时可改"列说明改动的代价。

| # | 口径 | 建议默认 | 何时可改 |
|---|---|---|---|
| **B1** | 分桶与排序 | **分层 + 组内加权**。桶判定：所有 HARD 均 PASS → `FULL_PASS`；存在 PASS_WITH_WARNING 且无 FAIL → `TOLERANCE`；存在 FAIL → `FAIL`。桶内 `weighted_score = Σ(w×s) / Σw`，只对**有数据**的指标求和；缺数据的指标不计权重但记 `missing_metrics`（缺一项扣 5% 展示分，不影响排名）。同分依次比：必测项少者 → `must_verify` 命中少者 → `candidate_id` 小者 | 只改计算函数，表结构不变。随时可改 |
| **B2** | 推荐规模 | **档位可配**，存在 `design_project.decision_capacity_mode` + `decision_capacity_value`：`RATIO`（按候选数比例，默认 `0.200`）或 `ABSOLUTE`（固定个数）。实际名额 = `min(湿实验余额, 档位算出的数)`，且至少 1。两个字段进基线块7（`quota_json`），随快照冻结 | 改参数即可，不必改表。若要支持第三种模式（如「至少 N 个」），加枚举值 + 校验分支 |
| **B3** | 状态机 | `DRAFT → CONFIRMED / DEFERRED / CANCELLED`；`DEFERRED → DRAFT`（补数据后重开）。`CONFIRMED` 是终态，改动走新版本 + `revision_of` | 加状态需改 DDL 注释与前端。终态语义不建议改 |
| **B4** | 回放粒度 | 必须**能重算出同一份名单**。存 `input_snapshot_hash`（全部证据包 hash 的排序聚合）+ `weights_snapshot` + `rule_version`。提供 `:replay` 端点比对 rank 与 outcome，差异非空则 `REPLAY_MISMATCH` | 若将来引入 LLM 参与排序，回放语义要改（LLM 输出不确定），届时需存完整 prompt + response |

### B 组里唯一需要你注意的坑

**B1 的"缺数据指标不计权重"会让候选之间不可比**：一个测了 8 个指标的候选和一个只测了 3 个的，加权分分母不同。展示时必须同时给出"已覆盖指标数"，否则用户看到的是"3 个指标全满分"排第一。这是设计上有意的取舍（宁可缺数据也不要补零分），但 UI 必须显式说明。

**B2 的档位有两种容易写错的输入**（已在基线校验里拦住，不靠前端自觉）：

| 写错 | 后果 | 拦法 |
|---|---|---|
| `RATIO` 填 `20`（把 20% 当百分数写） | 若不拦，决策会推荐出 2000% 的名额，比候选总数还多 | 报 `CAPACITY_RATIO_OUT_OF_RANGE`，并在文案里指路"想固定个数请改档位" |
| `ABSOLUTE` 填 `2.5` | "2.5 个候选"没有意义 | 报 `CAPACITY_ABSOLUTE_NOT_INTEGER` |

档位为空或模式无法识别时报 `NO_CAPACITY_MODE` / `CAPACITY_MODE_INVALID`，**不猜默认值** —— 与 `min_candidates` 去掉 `DEFAULT 10` 是同一原则。

## 5. 数据模型

### 5.1 新表

```sql
-- ---------------------------------------------------------------------------
-- 证据包：逐候选一份，不可变。只装引用与摘要，不装决策产物（A2）
-- ---------------------------------------------------------------------------
CREATE TABLE evidence_bundle (
    id                   BIGINT       NOT NULL AUTO_INCREMENT,
    bundle_no            VARCHAR(64)  NOT NULL,
    project_id           BIGINT       NOT NULL,
    round_id             BIGINT       NULL,
    candidate_id         BIGINT       NOT NULL,
    baseline_snapshot_id BIGINT       NOT NULL  COMMENT '需求基线（判定阈值来源）',
    evaluation_freeze_id BIGINT       NOT NULL  COMMENT '评估冻结快照（分数来源）',
    lineage_json         JSON         NULL      COMMENT 'root→当前 的 id + edit_reason，只存引用',
    constraint_verdict_json JSON      NULL      COMMENT '[{ruleId,operator,threshold,tolerance,policy,outcome,deviation}]',
    risk_flags_json      JSON         NULL      COMMENT '[{riskCode,severity,mustVerify,source}]',
    pending_items_json   JSON         NULL      COMMENT '客观遗漏项（由 must_verify 推导）',
    covers_metrics       INT          NOT NULL DEFAULT 0 COMMENT '已覆盖指标数（B1 展示用）',
    completeness         VARCHAR(16)  NOT NULL DEFAULT 'OK' COMMENT 'OK / PARTIAL / INCOMPLETE',
    content_hash         CHAR(64)     NOT NULL  COMMENT '以上内容 sha256（不含时间）',
    status               VARCHAR(16)  NOT NULL DEFAULT 'FROZEN' COMMENT 'FROZEN / SUPERSEDED',
    frozen_at            DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_bundle_no (bundle_no),
    UNIQUE KEY uk_candidate_hash (candidate_id, content_hash),
    KEY idx_project_round (project_id, round_id),
    KEY idx_freeze (evaluation_freeze_id)
) COMMENT='候选证据包（不可变，决策唯一输入）';

-- ---------------------------------------------------------------------------
-- 业务性否决规则（A1 第二层）
-- ---------------------------------------------------------------------------
CREATE TABLE decision_veto_rule (
    id           BIGINT       NOT NULL AUTO_INCREMENT,
    -- 全局规则用 0 而不是 NULL：唯一键含 NULL 时 MySQL 不做去重，
    -- NULL 种子每次重跑都会再插一遍（实测第二遍变成 12 条）
    project_id   BIGINT       NOT NULL DEFAULT 0 COMMENT '0 = 全局默认规则',
    rule_code    VARCHAR(40)  NOT NULL  COMMENT 'MUST_VERIFY_UNVERIFIED / BUDGET_EXCEEDED / ...',
    severity     VARCHAR(10)  NOT NULL DEFAULT 'BLOCK' COMMENT 'BLOCK / WARN',
    dimension    VARCHAR(30)  NULL,
    threshold_num DECIMAL(12,4) NULL,
    params_json  JSON         NULL,
    human_readable VARCHAR(500) NOT NULL COMMENT '红线 R2：不允许存在用户看不到的规则',
    enabled      TINYINT      NOT NULL DEFAULT 1,
    sort_no      INT          NOT NULL DEFAULT 0,
    created_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at   DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_project_rule (project_id, rule_code),
    KEY idx_project_enabled (project_id, enabled)
) COMMENT='决策阶段业务性否决规则';

-- ---------------------------------------------------------------------------
-- 决策记录：一次决策 = 一行
-- ---------------------------------------------------------------------------
CREATE TABLE decision_record (
    id                  BIGINT       NOT NULL AUTO_INCREMENT,
    decision_no         VARCHAR(64)  NOT NULL,
    project_id          BIGINT       NOT NULL,
    round_id            BIGINT       NULL,
    baseline_snapshot_id BIGINT      NOT NULL,
    report_id           BIGINT       NULL      COMMENT '关联的正式报告（报告审批与候选决策分离）',
    weights_snapshot    JSON         NOT NULL  COMMENT '排序用的指标权重快照（B4）',
    rule_version        VARCHAR(32)  NOT NULL  COMMENT '排序+否决规则版本（B4）',
    input_snapshot_hash CHAR(64)     NOT NULL  COMMENT '全部证据包 hash 排序聚合（B4）',
    replay_hash         CHAR(64)     NULL      COMMENT '确认时重算结果的 hash，用于回放比对',
    status              VARCHAR(16)  NOT NULL DEFAULT 'DRAFT' COMMENT 'DRAFT / CONFIRMED / DEFERRED / CANCELLED',
    selected_count      INT          NOT NULL DEFAULT 0,
    backup_count        INT          NOT NULL DEFAULT 0,
    rejected_count      INT          NOT NULL DEFAULT 0,
    deferred_count      INT          NOT NULL DEFAULT 0,
    decision_note       VARCHAR(2000) NULL,
    decided_by          BIGINT       NULL,
    decided_at          DATETIME     NULL,
    revision_of         BIGINT       NULL      COMMENT '上一版决策（改动走新版本，不覆盖）',
    version_no          INT          NOT NULL DEFAULT 1,
    created_at          DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at          DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_decision_no (decision_no),
    KEY idx_project_round (project_id, round_id),
    KEY idx_status (status),
    KEY idx_revision (revision_of)
) COMMENT='决策记录（CONFIRMED 后不可变）';

-- ---------------------------------------------------------------------------
-- 决策-候选明细：一个候选一行
-- ---------------------------------------------------------------------------
CREATE TABLE decision_candidate (
    id                BIGINT       NOT NULL AUTO_INCREMENT,
    decision_id       BIGINT       NOT NULL,
    candidate_id      BIGINT       NOT NULL,
    evidence_bundle_id BIGINT      NOT NULL,
    bucket            VARCHAR(16)  NOT NULL COMMENT 'FULL_PASS / TOLERANCE / FAIL',
    rank_no           INT          NULL      COMMENT '桶内排名；FAIL 桶为 NULL',
    weighted_score    DECIMAL(8,4) NULL,
    covers_metrics    INT          NOT NULL DEFAULT 0,
    missing_metrics_json JSON      NULL,
    outcome           VARCHAR(16)  NOT NULL COMMENT 'SELECTED / BACKUP / REJECTED / DEFERRED',
    reject_reason     VARCHAR(40)  NULL      COMMENT 'FILTER_REASON 字典（stage=DECISION）',
    manual_override   TINYINT      NOT NULL DEFAULT 0,
    override_reason   VARCHAR(500) NULL      COMMENT 'manual_override=1 时必填',
    created_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at        DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    UNIQUE KEY uk_decision_candidate (decision_id, candidate_id),
    KEY idx_decision_outcome (decision_id, outcome),
    KEY idx_candidate (candidate_id)
) COMMENT='决策明细（候选级取舍）';

-- ---------------------------------------------------------------------------
-- 否决命中：一个候选可能命中多条
-- ---------------------------------------------------------------------------
CREATE TABLE decision_veto_hit (
    id             BIGINT       NOT NULL AUTO_INCREMENT,
    decision_id    BIGINT       NOT NULL,
    candidate_id   BIGINT       NOT NULL,
    rule_code      VARCHAR(40)  NOT NULL,
    severity       VARCHAR(10)  NOT NULL,
    message        VARCHAR(500) NOT NULL,
    evidence_ref   VARCHAR(200) NULL COMMENT '指向证据包里的具体字段，便于追溯',
    created_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (id),
    KEY idx_decision_candidate (decision_id, candidate_id),
    KEY idx_rule (rule_code)
) COMMENT='否决命中明细';

-- ---------------------------------------------------------------------------
-- 风险接受：逐候选逐风险点（A3）
-- ---------------------------------------------------------------------------
CREATE TABLE risk_acceptance (
    id              BIGINT       NOT NULL AUTO_INCREMENT,
    decision_id     BIGINT       NOT NULL,
    candidate_id    BIGINT       NOT NULL,
    risk_code       VARCHAR(40)  NOT NULL,
    severity_at_accept VARCHAR(10) NOT NULL,
    reason          VARCHAR(1000) NOT NULL COMMENT '接受理由（必填）',
    accepted_by     BIGINT       NOT NULL,
    accepted_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
    valid_until     DATE         NULL      COMMENT 'NULL = 本决策内长期有效',
    PRIMARY KEY (id),
    UNIQUE KEY uk_accept (decision_id, candidate_id, risk_code),
    KEY idx_candidate (candidate_id)
) COMMENT='风险接受记录（must_verify 项不可接受）';
```

### 5.2 改造既有表

```sql
-- 报告级审批与候选级决策分离（见 §9）
-- 注意索引名：design_report 已有 idx_decision(project_id, decision) 用于报告审批，

-- 决策名额档位（B2）：放 project 而不是写死在代码里
-- RATIO = 按候选数比例（value 取 0~1），ABSOLUTE = 固定个数（value 取正整数）
-- 两个字段进块7（quota_json），随快照冻结 —— 中途改档位不影响已提交的决策
```

## 7. 判定流程（伪代码）

```java
// D2 + D3：复核与否决
for (EvidenceBundle bundle : bundles) {
    // 技术性复核：重算而不是采信生成阶段的结论
    List<Verdict> verdicts = constraints.stream()
        .map(rule -> boundaryJudge.judge(bundle.metricValue(rule), rule))
        .collect(toList());
    if (verdicts.anyMatch(v -> v.outcome == FAIL)) {
        vetoHits.add(HARD_RULE_VIOLATED);        // 兜底
    }

    // 业务性否决
    for (DecisionVetoRule rule : enabledVetoRules) {
        if (rule.matches(bundle, project)) vetoHits.add(rule);
    }
}

// D4：分桶与排序
Map<Bucket, List<Candidate>> buckets = candidates.stream()
    .filter(c -> !hasBlockVeto(c))               // BLOCK 级直接淘汰，WARN 不拦
    .collect(groupingBy(this::bucketOf));        // FULL_PASS / TOLERANCE / FAIL

for (Bucket bucket : List.of(FULL_PASS, TOLERANCE)) {
    List<Candidate> ranked = bucket.stream()
        .sorted(byWeightedScore(B1).thenByMustVerifyCount().thenById())
        .toList();
    // D5：名额分配
    ranked.forEach(c -> c.outcome = withinCapacity(c) ? SELECTED : BACKUP);
}
buckets.get(FAIL).forEach(c -> c.outcome = REJECTED);

// D8：回放指纹
String inputHash = sha256(sortedBundleHashes);
String replayHash = sha256(canonical(buckets, outcomes, ranks));
```

**关键**：`FAIL` 桶不参与排序也不占名额，但**必须保留**在 `decision_candidate` 里 —— 它们是回流阶段的负样本。"这个分子为什么被淘汰"和"这个分子为什么入选"同样有价值。

## 9. 与现有报告审批流的关系

**代码现状**（重构前遗留，`design_report` 表）：
- `decision`（PENDING/APPROVED/REJECTED）+ `decision_by` + `decision_at` + `decision_note`
- `ReportController` 有 `PATCH /{id}/decision`
- `candidate_molecule.review_status`：NEW / QUALIFIED / REJECTED / TOP / SELECTED

**三个选项**

| 方案 | 做法 | 评价 |
|---|---|---|
| ① 报告内嵌决策 | 在 `design_report.body_json` 里存决策结果 | ❌ 报告是**产物**，决策是**过程**。过程要能被重放和版本化，塞进 JSON 就失去了结构 |
| ② 决策独立 + 报告引用 | 新建 `decision_record`；`design_report.decision_id` 指向它；报告审批与候选决策各记各的 | ✅ 推荐 |
| ③ 完全替换 | 删掉 `design_report.decision` 系列字段，统一走决策表 | ❌ 破坏既有 77 项报告 E2E，且报告审批本身有独立语义（这份文档写得对不对 ≠ 这些分子该不该选） |

**采纳方案 ②，边界如下**

| 问题 | 谁回答 |
|---|---|
| 这份报告写得对不对、能不能对外发 | `design_report.decision`（不变） |
| 这批候选谁入选、谁淘汰、为什么 | `decision_record`（新增） |
| 某个分子最终定不定 | `candidate_molecule.review_status`，**由决策确认时同步写入** |

**同步规则**：`decision_record` 转 `CONFIRMED` 时，按 outcome 回写候选：
- `SELECTED` → `review_status = SELECTED`
- `REJECTED` → `review_status = REJECTED`
- `BACKUP` / `DEFERRED` → 不改动，保持原值

**矛盾状态的防御**：报告审批 `APPROVED` 但决策仍是 `DRAFT` 时，报告页必须显示"候选决策尚未确认"，且导出动作给出警告。这个是前端责任，后端在 `GET /reports/{id}` 里带出 `decisionStatus` 供判断。

## 10. 可回放要求（B4 落地）

**目标**：凭 `decision_record` 一行，能重跑出完全相同的候选名单、排名与结论。

| 存什么 | 为什么 |
|---|---|
| `input_snapshot_hash` | 全部证据包 `content_hash` 排序后的聚合值。任何一个证据包变了，hash 就不同 —— 能立刻发现"用另一版数据重算" |
| `weights_snapshot` | 指标权重会随项目演进变化。不存快照，重算时用的是今天的权重，结论必然不同 |
| `rule_version` | 排序与否决规则的版本号（如 `DR-1.2`）。规则改了就不能用旧结论 |
| `replay_hash` | 确认那一刻算出的结果指纹。`:replay` 时重算一次，比对不一致立即报错 |

**回放失败的三种原因，处理不同**

| 原因 | 处理 |
|---|---|
| 证据包被 SUPERSEDED（重新评估过） | 预期行为：提示"证据已更新，请基于新版重新决策"，不报错 |
| 权重被改 | 提示"权重已变更"，允许用旧 `weights_snapshot` 强制重放以验证历史结论 |
| 规则版本不一致 | 拒绝重放，明确告知版本差异 |

## 11. 回流沉淀的预留点

决策阶段是负样本的主要产地。以下字段**现在就留好**，回流阶段（06 未覆盖）才有东西可聚合：

| 字段 | 回流用途 |
|---|---|
| `decision_candidate.bucket` | 统计"多少候选连容差区都进不了" → 判断生成策略是否偏离 |
| `decision_candidate.reject_reason` | 聚合 TOP-N 淘汰原因 → 更新负向模式库 |
| `decision_veto_hit.rule_code` | 统计哪条否决规则最常触发 → 是否阈值过严 |
| `risk_acceptance.risk_code` | 统计被接受最多的风险类型 → 该风险可能是可容忍的，阈值可放宽 |
| `decision_record.rule_version` | 比较不同规则版本的决策质量 → 规则演进效果 |

> "每轮结果都能回流"的前提是**淘汰也能被解释**。所以 `reject_reason` 与 `filter_reason` 一样是必填项，不是可选项。

## 12. 前端设计

```
决策页 /design/projects/:projectId/decisions/:decisionId
├── ① 决策头      status / 版本 / 名额使用情况（SELECTED 3 / 名额 8）
├── ② 分桶总览    三桶计数 + 加权分分布条，一眼看出"有没有可选的"
├── ③ 候选明细
│    ├─ 每个候选：bucket 徽章 + rank + weighted_score + 已覆盖指标数
│    ├─ 否决徽章（红色 BLOCK / 黄色 WARN），hover 显示 message 与 rule_code
│    ├─ outcome 下拉（SELECTED / BACKUP / REJECTED / DEFERRED）
│    └─ 人工调整必须填理由（前端强校验，后端 400 兜底）
├── ④ 风险接受    逐候选逐个 risk_code 勾选 + 理由输入；must_verify 项禁用并说明原因
└── ⑤ 确认区
     ├─ 汇总：入选 N / 备选 M / 淘汰 K / 暂缓 J
     ├─ 阻断项：还有 BLOCK 级否决时按钮禁用并列出
     └─ 回放校验：确认前自动跑一次 :replay，不一致则展示差异
```

**关键交互约束**

1. **淘汰必须有原因**：把候选改成 `REJECTED` 时，`reject_reason` 下拉必选。默认值为空而不是"其他" —— 有默认值就等于没人会认真选。
2. **人工覆盖要显眼**：`manual_override=1` 的行整行加左边框标记，复核时一眼能看到"这几行是机器判的，这几行是人改的"。
3. **缺数据要说清**：`coversMetrics` 小于总指标数的候选，分数旁显示"基于 3/8 个指标"，避免用户误以为满分。
