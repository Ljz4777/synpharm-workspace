## 0. 本次决策与范围

### 0.1 架构决策（已确认）

**基础套件保持分离，主业务合并为一个服务。**

| 保留独立 | 合并进主业务服务 |
|---|---|
| `gateway`（网关、鉴权、CORS、路由） | `design`（主业务本体） |
| `auth`（身份与用户） | `asset`（文件资产，3 个内网端点、0 调用方） |
| `predict`（预测域，独立调 FastAPI） | `platform`（工具注册表，1 张表、被 design 调 1 次） |
| mysql / redis / rabbitmq / nacos | |

收敛后 Java 进程：**4 个**（gateway / auth / predict / core），相比现在的 6 个减少 2 个。

**理由**：主业务的四段（需求→生成→编辑→决策）全部落在 design 域，跨服务调用会变成"为了分层而分层"。asset 与 platform 本就是 design 的支撑件，独立存在没有业务理由。

### 0.2 数据分离决策

主业务合并表：`synpharm_design` + `synpharm_asset` + `synpharm_platform` → **`synpharm_core`**。

`auth`、`predict` 保持独立 schema。

合并收益：**可以建真外键了**。现在 `evaluation_result.source_tool_id → design_tool.id` 因为跨 schema 无法建约束（36 号脚本明确写了「跨 schema 外键禁止」），合并后可以补上。

### 0.3 明确不做的事

- 不动 `gateway` / `auth` / `predict` 的内部实现（只改路由指向）
- 不做评估体系（只做**最小评估**，见 §5.1）
- 不做证据打包 / 决策（另见 **07**）、报告 / 回流（仍未设计）
- 不引入 Agent 框架（S3/S9/E7 的 Agent 介入点先留接口，用规则实现）

### 0.4 一个必须先定的依赖

编辑阶段的设计**每一步都依赖评估**（E0 准入要求「已完成全维度评估」，E1 输入是分数+置信度，E3 要预测影响，E6 是 Δ 对比）。

本次采用 **最小评估**：只用 RDKit 算理化性质 + 硬约束判定，能产出 `evaluation_freeze`，但**没有置信度、没有结构归因**。这样编辑链能跑通主干，`attribution` 字段先留空。详见 §5.1。

## 1. 服务收敛

### 1.1 目标结构

```
synpharm-cloud/
├── synpharm-common          ← 共享（Result / ErrorCode / CurrentUser / 过滤器）
├── synpharm-gateway         ← 网关（唯一入口）
├── synpharm-auth            ← 身份（独立）
├── synpharm-predict         ← 预测域（独立）
└── synpharm-core            ← 主业务（design + asset + platform 合并）
    ├── design/              ← 需求分析、生成、编辑、候选、轮次、约束…
    ├── asset/               ← 文件资产
    └── platform/            ← 工具注册表 + 能力矩阵
```

包结构建议：

```
com.synpharm.core
├── SynpharmCoreApplication
├── design    (api / application / domain / infrastructure)
├── asset     (api / application / domain / infrastructure)
└── platform  (api / application / domain / infrastructure)
```

### 1.2 网关路由变化

| 现状 | 收敛后 |
|---|---|
| `/api/design/**` → `lb://synpharm-design` | `/api/design/**` → `lb://synpharm-core` |
| `/api/design/tools/**` → `lb://synpharm-platform`（**必须排在 design 之前**） | 合并，**这条前置路由可以删** |
| `/api/design/capabilities` → `lb://synpharm-platform` | 合并 |
| `/api/system/**` → `lb://synpharm-platform` | `/api/system/**` → `lb://synpharm-core` |
| `/internal/files` → asset 服务（网关不路由） | 进程内调用 |

**这是一处实打实的简化**：现在「`platform-design-tools` 路由必须排在 `design` 之前，否则 `/api/design/tools/**` 被静默吃掉成 404」这个坑，合并后自然消失。

### 1.3 要删掉的跨服务代码

| 现有 | 处理 |
|---|---|
| `design/infrastructure/client/ToolRegistryClient.java` | **删除**，改进程内调用 `ToolRegistryService` |
| `ToolRegistryClient` 的 503 `DEPENDENCY_UNAVAILABLE` 降级分支 | **删除**（不再有网络失败可能） |
| `platform/.../InternalToolController` 的 `/internal/tools/registry` | **删除**（无消费方） |
| `asset/InternalFileController` 的 `X-Internal-Token` 校验 | 保留（同进程也要防越权），但调用方式改成接口 |
| 两份 `SimpleCircuitBreaker`（platform / predict 各一份） | predict 的那份保留；platform 那份随 FastAPI 探测保留（仍要调外部容器） |

### 1.4 数据迁移顺序

```
1. 建库 synpharm_core，建账号，授权
2. mysqldump synpharm_design / synpharm_asset / synpharm_platform → 导入 core
3. 补跨包外键（原本因跨 schema 建不了的那些）
4. 各服务 datasource 指向 core
5. 验证：**21 张表**行数一致、外键生效、端点回归
6. 旧库保留 7 天后 DROP
```

> **风险**：`evaluation_result.source_tool_id → design_tool.id` 补外键时，若历史数据有孤儿行会失败。36 号脚本刻意没建，理由是「工具下线时历史结果要保留」。**建议这条外键仍然不建**，改成逻辑引用 —— 与现有设计保持一致。

## 3. 需求分析过程

### 3.1 业务流

```
输入                          处理                        输出
─────────────────────────────────────────────────────────────────
靶点（名称/MOA/适应症）        选靶点 → 校验序列完整性       ┐
分子类型（小分子/抗体/…）      选 MODALITY → 带出默认维度     │
项目约束                      选/建约束集 → 逐条确认          ├─► baseline_snapshot
成功标准                     选 OBJECTIVE → 定阈值+误差带    │   （八块冻结）
评估指标                      按 MODALITY 默认 + 手工增删     │
风险关注点                    结构化录入                     ┘
```

**关键动作：冻结**。`DRAFT → READY` 时生成 `baseline_snapshot`，之后所有生成任务**只读快照，不读项目当前状态**。用户中途改约束不影响已提交的任务。

这与生成设计 S0 的「只读快照，不读项目当前状态。用户中途改约束不影响本任务」完全一致。

### 3.2 baseline_snapshot 的八块

生成设计里写「校验八块完整性」但只列了 6 块。我补齐为 8 块：

| # | 块 | 来源 | 校验 |
|---|---|---|---|
| 1 | 靶点 + 主靶点角色 | `project_target` | 必须恰好 1 个 `is_primary=1` |
| 2 | 靶点结构 + 口袋 | `target_structure` / `binding_pocket` | 至少 1 个可用结构；口袋可选 |
| 3 | 分子形式 | `design_project.modality_id` | 必填，且 `design_library_item` 存在 |
| 4 | 硬约束 | `constraint_rule` where `severity=HARD` | **≥1 条** |
| 5 | 软约束 + 权重 | `constraint_rule` where `severity=SOFT` | 可为空 |
| 6 | 评估指标清单 | `project_metric` | ≥1 条，且指标码在 `metric_definition` 存在 |
| 7 | 生成配额 + 最小候选数 | `design_project.quota_*` / baseline 参数 | 配额 > 0，`min_candidates` ≥ 1 |
| 8 | 风险关注点 | `project_risk_item` | 可为空 |

> 第 6、7 块正是我此前指出的「需求分析缺失的两个输出」。补上后八块成立。

### 3.3 表结构

#### `baseline_snapshot`（新建）

```sql
CREATE TABLE baseline_snapshot (
    id                  BIGINT PRIMARY KEY AUTO_INCREMENT,
    snapshot_no         VARCHAR(64)  NOT NULL COMMENT '快照编号 BS+yyMMddHHmmss+随机',
    project_id          BIGINT       NOT NULL,
    project_version     INT          NOT NULL COMMENT '冻结时的项目版本号',
    user_id             BIGINT       NOT NULL COMMENT '冻结操作人',

    -- 八块内容（冻结副本，不可变）
    targets_json        JSON         NOT NULL COMMENT '块1: 靶点列表+主靶点角色',
    structure_json      JSON                  COMMENT '块2: prep 后的结构 URI/SHA256/口袋',
    modality_code       VARCHAR(30)  NOT NULL COMMENT '块3: 分子形式',
    hard_rules_json     JSON         NOT NULL COMMENT '块4: 硬约束快照（≥1 条）',
    soft_rules_json     JSON                  COMMENT '块5: 软约束+权重',
    metrics_json        JSON         NOT NULL COMMENT '块6: 指标清单+权重',
    quota_json          JSON         NOT NULL COMMENT '块7: GPUh/湿实验名额/min_candidates',
    risks_json          JSON                  COMMENT '块8: 风险关注点',

    -- 冻结元信息
    completeness_json   JSON         NOT NULL COMMENT '逐块校验结果 {block: ok|missing}',
    content_hash        CHAR(64)     NOT NULL COMMENT '八块内容的 sha256，用于幂等与审计',
    status              VARCHAR(20)  NOT NULL DEFAULT 'ACTIVE'
                        COMMENT 'ACTIVE/SUPERSEDED（被新版本取代）',
    superseded_by       BIGINT                COMMENT '被哪个快照取代',
    created_at          DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,

    UNIQUE KEY uk_snapshot_no (snapshot_no),
    UNIQUE KEY uk_project_version (project_id, project_version),
    KEY idx_project_status (project_id, status),
    CONSTRAINT fk_bs_project FOREIGN KEY (project_id) REFERENCES design_project(id)
) COMMENT='需求基线快照（冻结）';
```

**为什么用 JSON 而不是拆 8 张表**：快照是**不可变副本**，不需要被 join 查询，只需要整体读取和哈希比对。拆表会让幂等校验（`content_hash`）变复杂。

### 3.4 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| `POST` | `/api/design/projects/{id}/baseline:preview` | 预检八块完整性，返回缺项清单（不落库） |
| `POST` | `/api/design/projects/{id}/baseline:freeze` | 冻结，生成 `baseline_snapshot`，`project.status` → `READY` |
| `GET` | `/api/design/projects/{id}/baseline` | 取当前 ACTIVE 快照 |
| `GET` | `/api/design/projects/{id}/baselines` | 历史快照列表 |
| `GET/POST/PATCH/DELETE` | `/api/design/projects/{id}/metrics` | 项目指标 CRUD |
| `GET/POST/PATCH/DELETE` | `/api/design/projects/{id}/risks` | 风险点 CRUD |
| `POST` | `/api/design/projects/{id}/constraints:attach` | 绑定约束集（已存在，需补） |

**`freeze` 的幂等**：同一 `project_version` + 相同 `content_hash` 重复调用返回已有快照，不产生第二条。

### 3.5 边界值语义（补 `constraint_rule`）

编辑设计里那个「真实的坑」必须在需求阶段解决：`affinity ≤ 100 pM`，预测 110 pM —— 算不算达标？

```sql
ALTER TABLE constraint_rule
    ADD COLUMN tolerance       DECIMAL(14,5) NULL COMMENT '方法学误差带；NULL=无容差',
    ADD COLUMN boundary_policy VARCHAR(20)   NULL DEFAULT 'STRICT'
        COMMENT 'STRICT=严格比较 / WITHIN_TOLERANCE=容差内视为达标 / ESCALATE_TO_SOFT=交给决策判断',
    ADD COLUMN applies_to_modality VARCHAR(60) NULL COMMENT '适用分子形式，逗号分隔；NULL=全部';
```

判定逻辑（**代码实现，不由 Agent 判定**）：

| policy | 判定 |
|---|---|
| `STRICT` | `110 > 100` → 不达标，`passed=0`，综合分 0 |
| `WITHIN_TOLERANCE` | `110 ≤ 100 + tolerance` → 达标，但 `boundary_warning=true` |
| `ESCALATE_TO_SOFT` | 不进 `hard_passed`，转为 soft 扣分，由决策阶段人工判断 |

### 3.6 状态机

```
design_project.status
  DRAFT ──freeze()──► READY ──首个 generation 提交──► ACTIVE
    ▲                  │                                │
    │                  └──(需求变更)──► DRAFT            ├──结项──► COMPLETED
    └───────────────────────────────────────────────────┘         └──► ARCHIVED
```

**约束变更 = 新版本项目**（编辑设计的铁律三）：
- 已冻结后再改约束 → `project_version + 1`
- 旧 `baseline_snapshot` 置 `SUPERSEDED`
- 所有 `candidate_molecule` 置 `needs_re_eval=1`

## 4. 生成过程

### 4.1 十步流水线

严格按设计文档，不改动顺序与闸门：

| 步 | 名称 | 执行者 | 闸门 |
|---|---|---|---|
| S0 | 基线校验与任务登记 | 引擎（确定性） | 八块完整 + 工具可用 + 配额 > 0 |
| S1 | 结构准备 | 引擎（prep 工具） | 结构不可修复 → failed；pLDDT<70 → degraded |
| S2 | 搜索空间定义 | 引擎（规则+库检索） | 空间为空 → failed |
| S3 | 生成策略拟定 | **Agent①** | 参数校验失败重拟 2 次 → 降级默认模板 |
| S4 | 分片执行 | 引擎（调度器+队列） | 实时扣 GPUh，超 cap 即停 |
| S5 | 去重 | 引擎 | 不会失败 |
| S6 | 粗筛 | 引擎 | 剩余 = 0 → 提示回 S2/S3 |
| S7 | 多样性配额 | 引擎 | 有效簇 < 3 → 严重告警但放行 |
| S8 | 登记与快照 | 引擎 | 打 `generation_output_snapshot` |
| S9 | 漏斗解读 | **Agent②** | verdict 由代码算，LLM 只写文案 |

**四条工程纪律**（设计原文）：
1. 幂等：同一 `idempotent_key` 不产生第二份候选集
2. 缓存优先：`(tool_id + param_hash + input_hash)` 命中即复用
3. 原因必记：被筛分子必须有 `filter_reason`
4. Agent 只出现两次：S3 选策略、S9 写诊断

### 4.5 `sequence_hash` 的定义要改

现有是「单条序列的 sha256」。抗体有重链+轻链，双抗有 3~4 条链。定义改为：

```
sequence_hash = sha256( 规范化(heavy_chain) + "|" + 规范化(light_chain) + "|" + Σ规范化(extra_chains按名字排序) )
```

规范化 = 去空白 + 大写 + 去尾部终止符。小分子场景该字段为 NULL（仍用 `inchikey` 去重）。

## 5. 编辑过程

### 5.1 前置：最小评估

编辑的输入契约要求 `snapshot_id`（评估冻结快照）。本次做**最小评估**：

| 做 | 不做 |
|---|---|
| RDKit 算理化性质（MW/LogP/TPSA/QED/SA/PAINS/BRENK） | 亲和力预测（需 DTI 模型） |
| 硬约束判定（阈值 + 误差带） | 免疫原性预测 |
| 产出 `evaluation_freeze` | 置信度 / 适用域 / 结构归因 |
| 综合分计算（权重归一化） | 多轮迭代评估 |

**后果**：E1 的 `attribution`（归因到结构特征）、E3 的「预测对已达标维度的影响」在本次只能留空或走规则近似。文档中标注 `[待评估体系]` 的字段先置 NULL。

### 5.2 E0~E7

| 步 | 名称 | 执行者 | 输出 |
|---|---|---|---|
| E0 | 准入闸门 | 引擎 | 5+1 项检查 |
| E1 | 诊断归因 | 引擎（确定性）+ Agent 写文案 | `edit_gap_report` |
| E2 | 策略匹配 | 引擎（读映射表） | 候选动作 top-3 |
| E3 | 影响面评估 | 引擎 | `edit_impact_assessment`（PASS/WARN/BLOCK） |
| E4 | 设计空间枚举 | 引擎 | 规模 + 剪枝后规模 |
| E5 | 空间内快筛 | 引擎 | `edit_batch` + pre_score + filter_reason |
| E6 | 执行与对照 | 引擎 | `edit_delta_report` |
| E7 | 编辑后诊断 | **Agent③**（只写文案） | verdict: PASS / PASS_WITH_RESIDUAL / FAIL |

### 6.3 关键交互

**① 冻结前必须回答边界值语义**

`BaselineWizard` 第 4 步（指标/目标）里，每条硬约束旁边有一个必填项：

```
亲和力   ≤ [100] pM    容差 [___]   判定方式 (严格 ▾)
```

三种判定方式的选择必须显式，不能默认。**这是设计里那个「真实的坑」在 UI 层的落地** —— 模糊地带在立项时消除。

**② 生成提交后展示漏斗，而不是只报成功**

`GenerationDiagnosis.vue` 的核心是一个四段漏斗：

```
生成 10000 ──去重──► 8200 ──粗筛──► 1900 ──配额──► 120
          (18%)        (77%)        (94%)
                                            有效簇数 4 ✓
                                            缓存命中率 62%
```

每段可点开看 **filter_reason 分布**（`GET /generations/{id}/candidates?outcome=FILTERED`）。

**③ 编辑页以「缺口」为入口，不是以「序列」为入口**

这是设计里最重要的一条交互原则：「把『我觉得该这么改』转化为『哪个维度没达标、由什么结构特征导致』」。

`GapPanel` 列缺口，点一条 → `ActionPicker` 出动作 → 选动作 → 影响面预览（PASS/WARN/BLOCK）→ 确认 → 提交批次。

**用户不能直接改序列** —— 只能从映射表给的动作里选。`MoleculeEditor.vue` 保留为「查看改动点」的只读组件。

**④ 版本树要能看出 abandoned**

```
v1 ─┬─ v2 (side_chain @CDR3) ── v3 ✅ 当前
    └─ v2b (humanization) ⚠️ abandoned（affinity 掉出守卫）
```

**落地时发现并修掉的 6 个真缺陷**（都是本轮引入，不是历史遗留）

1. **硬约束全部静默失效（最严重）**。`baseline_snapshot.hard_rules_json` 里的 `paramsJson` 是**二次编码**的（约束表 `params` 本是 JSON 列，装配快照时又整体塞进去，落地形态是「字符串里装着 JSON 文本」）。解析端按 Map 取值 → 拿到空 Map → 所有 `NUMERIC_RANGE` 在 S6 被当成「字段映射不上」跳过。实测表现：**甲醇（MW=32）通过「MW 150~600」并被判为合格候选**，而全程无异常、无日志。修法：抽出 `HardRuleParser`，显式区分 Map / JSON 文本 / 缺失三种形态；并规定「拿不到就是 null，不返回空 Map」。用 `HardRuleParserTest` 锁住。
2. **「判不了的规则」对外不可见**。`PreFilterStage.Result.skippedRules` 有字段但无任何消费者，违反「没检查 ≠ 检查通过」这条纪律。修法：把 SKIPPED 汇总写进 `run.error_msg`，文案明写「以下规则未能判定（不是通过）」。
3. **`generation_run.strategies` NOT NULL 且无默认值** → 首次 insert 直接 500。S0 阶段尚未定策略（S3 才产出），修法：insert 时先占位 `PENDING`，S3 覆盖。
4. **失败任务卡在 PENDING**。`submit` 上有 `@Transactional(rollbackFor = Exception.class)`，S0~S3 抛异常时连 FAILED 状态一起回滚，库里只剩一条永远 PENDING 的记录（配额不释放、无法判断能否重试）。修法：**去掉该事务**（生成是同步长流程，一致性靠状态机表达而非事务边界），并加 `markFailed` 显式收尾。
5. **`seeds` 的 `@NotEmpty` 与自身 javadoc 矛盾**。javadoc 写「为空则自动取项目内已有候选」，注解却禁止为空 → 用户永远看不到「搜索空间为空」这条可操作提示（先被参数校验拦掉）。修法：删注解，让「两者皆空」由 S2 抛业务错误。
6. **校验顺序反了**。`resolveRound` 在 `resolveBaseline` 之前，未冻结项目报的是「没开轮次」而不是「没有基线」，把真正缺的东西藏起来。修法：先基线后轮次。
