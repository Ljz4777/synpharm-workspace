## 0. 一句话结论

> **v1.1 更新（2026-10-24）**：P0 + P1 中"只要 RDKit"的部分已实现 —— `capabilities` / `properties` / `chemistry.standardize` 三个端点上线，

v1.1 起 `capabilities` 已存在，这条"状态压平"的根因消除。

## 2. 缺口分层

按「阻塞范围 × 修复成本」排序。**L1 是枢纽，不修它其余努力都看不出效果。**

```
L0 运行态      容器停着              → 一切探测报 SERVFAIL
L1 契约枢纽    capabilities 不存在    → 12 工具全 available=0（★ 最高杠杆）
L2 引擎部署    crem/p2rank/vina/admet → 4 类能力整体不可用
L3 模型权重    FlashPPI 缺权重        → PPI 单点不可用
L4 契约不一致  错误格式/fail-open/文档端点/常量时间 → 与 Java 侧对不上，且是安全隐患
L5 测试        零测试               → 上面任何一项改动都没有回归网
L6 校准管线    feedback/* 全套缺失    → 湿实验回灌闭环走不通
```

### L0 运行态

| 项 | 现状 | 恢复成本 |
|---|---|---|
| 容器状态 | `Exited (137)` | `docker compose --env-file .env -f synpharm-deploy/docker-compose.dev.yml up -d fastapi` |

> **注意**：只做这一步**不会**改善任何工具状态 —— 探测错误会从 `SERVFAIL` 变成 `404 Not Found`，
> 12 个工具仍然全是 `available=0`。原因是 L1。

### L1 契约枢纽：`GET /v1/evaluate/capabilities`

**这是整份清单里唯一「投入产出比极高」的项。**

| 事实 | 说明 |
|---|---|
| 谁在调 | `platform/infrastructure/client/CapabilityProbeClient.java` → `.uri("/v1/evaluate/capabilities")` |
| 多久调一次 | `@Scheduled(fixedDelayString = "${platform.probe.interval-ms:600000}")`，默认 10 分钟 |
| 干什么用 | 回写 `design_tool.available` 与 `probe_msg`，是**红线 R1「能力真实性」的唯一数据源** |
| 契约 | [04 §2.1](../synpharm-deploy/docs/design/detailed/04-计算层契约与校准协议.md)，返回 `probedAt` / `engines` / `models` / `endpoints` 四段 |
| 现状 | **端点不存在，`api/v1/` 下连 `evaluate` 目录都没有** |
| 副作用 | 探测失败 → `ToolRegistryService` 捕获后统一写 `引擎不可达：<原因>` → 12 个工具全部 `available=0` |

**关键点**：`EngineCapabilities` DTO（Java 侧）的 `endpoints` 字段本来就能表达
`READY` / `NOT_IMPLEMENTED`。也就是说，**契约从设计上就允许「这个端点还没做」**，
缺失的只是 Python 侧把这个事实说出来。

补上约 30 行（纯静态能力表 + 复用现有 `get_model_status()`），收益是：

- 12 个工具从「全部引擎不可达」变成**如实反映**：
  `predict_dti`/`predict_ddi` = 可用，`predict_ppi` = `weights_missing`，其余 8 个 = `NOT_IMPLEMENTED`
- 前端第一次能区分「功能没做」和「服务挂了」
- 台账里 `probe_msg` 那 12 行 `SERVFAIL` 噪声消失

**硬约束**（04 §2.2 已定，实现时别忘）：

1. **必须复用** `services/algorithm_adapters.py::get_model_status()`，不要另写一套判定；
2. **不得触发权重加载** —— 只读文件存在性，`loaded` 是观测值不是判定值；
3. P95 < 50 ms（纯本地检查 + 常量表），因为后端每 10 分钟拉一次；
4. 无副作用、幂等，`X-API-Key` 必需。

### L4 契约不一致（4 项，且都与 Java 侧有耦合）

这一层不是「缺端点」，是**已经存在的端点与文档/下游说不一致**，容易在改的时候踩雷。

#### L4-1　错误响应格式：`detail` 是字符串，契约要对象

**现状**（`core/exceptions.py`）：

```python
return JSONResponse(status_code=exc.code,
                    content={"status": "error", "detail": exc.message})
#                                              ^^^^^^^^^^^^^^ 纯字符串
```

**04 §6 要求**：

```jsonc
{ "detail": { "errorCode": "SEQUENCE_TOO_SHORT", "message": "...",
              "algoType": "DTI", "field": "target_seq", "details": {...} } }
```

**耦合点（重要）**：`predict/infrastructure/client/FastApiClient.java::extractDetail()`

```java
JsonNode detail = node.get("detail");
return (detail != null && !detail.isNull()) ? detail.asText() : null;
```

`JsonNode.asText()` 对 **ObjectNode 返回空字符串**。所以如果 Python 侧单方面把 `detail`
改成对象，Java 侧拿到的会是 `""`，**错误文案全丢**，`translateError` 会退化成
`"预测模型未就绪"` / `"预测输入无效"` 这类兜底文案。

**因此改这一项必须两边一起改**，Java 侧加 `detail.isObject() ? detail.get("message").asText() : detail.asText()`
即可向后兼容。这条务必写进实施工单，否则是个静默降级。

#### L4-2　API Key 校验是 fail-open

**现状**（`core/auth.py`）：

```python
valid_keys = settings.api_key_list
if not valid_keys:
    return          # ← 没配 Key 就完全不校验
```

**04 §5 要求 fail-closed**（问题总账 `B-10`：「生产默认无认证」）。

现状的缓解条件是 `.env` 里已经配了 `FASTAPI_API_KEY=277f...`（32 位 hex），
且 platform/predict 两端一致，所以**当前实际是开着的**。但只要有人清空该变量，认证就静默消失。

#### L4-3　`X-API-Key` 比较非常量时间

```python
if api_key not in valid_keys:   # 列表成员判断，逐元素短路
```

04 §5 要求 `hmac.compare_digest`（`B-19`）。

#### L4-4　`/docs`、`/redoc`、`/openapi.json` 无条件暴露

`main.py` 里 `docs_url="/docs"` / `redoc_url="/redoc"` / `openapi_url="/openapi.json"` 全部硬编码开启，
04 §5 要求生产关闭或加鉴权（现状裸奔）。

> 这一项在 dev compose 里是可接受的（只映射 `18050` 到宿主），但生产 compose 若直接复用同一镜像就会泄漏完整 API 结构。

#### 附带发现（勘误）

04 §4.4 提到了 `POST /v1/feedback/activate` 与 `POST /v1/feedback/rollback`，
但 **§1「端点总清单」表里没有登记这两个**。实施校准管线时需要把 §1 表补全，
否则按表实现会漏掉激活/回滚。

### L5 测试：零测试

`H-05` 原始条目。当前 `synpharm-fastapi` 下没有任何测试文件。这导致：

- 上面 L1~L4 任何一项改动都**没有回归网**（Java 侧 364 个单测完全覆盖不到 Python）
- 04 §7 已明确要求「新端点必须附 pytest」

最低要求（按 04 §7）：能力矩阵、properties（含 Sanitize 失败降级）、edit（含非法结构）、
calibration（装载/激活/回滚/版本不匹配）。

### L6 校准管线：`feedback/*` 全套缺失

04 §4（Q4）给出了完整协议 —— manifest 结构、内容寻址存储、白名单 URI、LRU 20 版、
可复现性闭环（预测响应回传 `calibrationId`）。**三个端点一个都没实现**。

依赖关系：湿实验回灌 `POST /api/design/experiments/{id}/feedback`（design 第 12 组，3/7 未实现）
→ 调 `feedback/calibrate` → 上传工件 → `feedback/apply`。**这一整条链是断的**。

## 5. 解锁路线

分 6 批，**严格按依赖顺序**，每批可独立验收。

### 批 0：让容器活着（5 分钟）

```bash
docker compose --env-file .env -f synpharm-deploy/docker-compose.dev.yml up -d fastapi
curl -fsS http://localhost:18050/health/
```

**验收**：`/health/` 返回 `{"status":"degraded","summary":{"weights_missing":["ppi"]}}`。
**预期**：platform 探测错误从 `SERVFAIL` 变成 `404`，工具状态**不变**（这是预期的，别误判成修好了）。

### 批 1：`capabilities`（★ 最高杠杆，约 30 行 + 1 个 pytest）

按 04 §2 实现 `GET /v1/evaluate/capabilities`，复用 `get_model_status()`，`endpoints` 用常量表硬编码。

**验收**：
```sql
SELECT tool_code, available, probe_msg FROM design_tool WHERE deleted = 0;
-- predict_dti / predict_ddi → available=1
-- predict_ppi              → available=0, probe_msg='weights_missing: ...model.safetensors'
-- 其余 9 个                 → available=0, probe_msg='NOT_IMPLEMENTED'
```
**这是唯一一批能「不改任何 Java 代码就让 12 行台账变准」的改动。**

### 批 2：`evaluate/properties`（RDKit，已经装好）

一次点亮 8 个评估指标 + 3 个工具（`mol_properties` / `mol_diversity` / 部分 `admet` 替身不算）。
按 04 §3.1 契约实现，注意四条硬约束（`success=false` 不填充 0 值、PAINS/BRENK 给 SMARTS

**验收**：design 第 8 组（分子编辑 8）可以开工。

### 批 4：`feedback/*`（校准管线）

`file://` 白名单前缀、sha256 校验、LRU 20 版、预测响应回传 `calibrationId`。

**验收**：design 第 12 组剩下 2 个 feedback 端点 + 报告能标注校准版本。

### 9.3 三个必须记下的实现约束

| 约束 | 为什么 |
|---|---|
| **`engines` 的值必须是布尔** | 后端 `EngineCapabilities.engines` 是 `Map<String, Boolean>`。返回 `{available, version}` 对象会让整个能力矩阵反序列化失败，12 个工具**全部**判不出（比原来的全 0 更难排查）。版本号另放 `engineVersions` |
| **`models.ready` ≠ `loaded`** | 模型懒加载，「权重在但还没加载」是**正常可用**。初版把 `ready` 写成 `state=="ready"`（即已加载），导致 `predict_dti` / `predict_ddi` 权重齐全却被判未部署 —— 假阴。现为 `ready = 权重存在且未加载失败`，并有单测钉住 |
| **`SA_SCORE` 不可得，不冒充** | Ertl 的合成可及性评分依赖 `fpscores.pkl.gz`（RDKit Contrib），pip 版 rdkit 不含，且当前环境 GitHub 不可达。`SA_SCORE` 显式列入 `unsupported` 并说明原因；同时提供 `COMPLEXITY_PENALTY`（SA score 的复杂度罚项，RDKit 原生可算），**命名刻意不同**。请求 `SA_SCORE` 时整批 400，不静默跳过 |

### 9.4 测试

`tests/test_chemistry_api.py`，**19 项**，零额外依赖（stdlib `unittest`）：

```
docker exec -w /app synpharm-dev-fastapi python -m unittest discover -s tests -v
```

覆盖：数值权威值（阿司匹林 MW 180.16 / 咖啡因 InChIKey）、坏分子不中断整批、
`SA_SCORE` 整批拒绝、`engines` 布尔类型、`ready` 语义、去盐后 InChIKey 一致、
两种写法同一 InChIKey、ECFP 聚类合并关系、批量上限。

**为什么直连真实端口而不是 `TestClient`**：镜像里 `httpx 0.28.1` 与 `starlette 0.27.0`
不兼容（`Client(app=...)` 已被移除），`TestClient(app)` 直接抛 TypeError。这是既有的
环境问题（属 A 类），升级 starlette 有回归风险，而直连端口反而更接近生产。
